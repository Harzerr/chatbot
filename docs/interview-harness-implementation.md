# AI 面试 Harness 实现说明

## 1. 文档结论

当前项目已经实现了一套面向 AI 模拟面试的 Agent Harness 基础能力：

- 使用 LangGraph 和 SkillRegistry 组织 Agent 路由与技能执行。
- 使用结构化状态承载岗位、轮次、JD、简历、历史问答和工具结果。
- 使用 Mem0、Qdrant 和本地题库构建上下文与检索链路。
- 使用规则门控和 Prompt 约束限制问题数量、面试轮次、代码题切换和结束条件。
- 使用 Judge0 提供代码执行证据，并使用结构化 Rubric 对回答进行评估。
- 使用租户隔离、超时、重试、降级和 AI 请求指标提高服务可用性。

这里的 Harness 指围绕 LLM 建立的运行时控制层，而不是简单调用一次模型。它负责准备上下文、约束模型行为、编排工具、验证模型结果并记录运行指标。

## 2. 实际请求链路

```text
用户请求
  ↓
ChatAgent.ask
  ├─ Mem0 检索用户长期记忆
  ├─ Qdrant 检索当前会话历史
  └─ 生成 AgentState
       ↓
LangGraph
  ├─ Supervisor / SkillRegistry 路由
  └─ InterviewSkillRunner
       ↓
InterviewSkill
  ├─ 解析岗位、轮次、JD 和简历上下文
  ├─ 检索岗位知识和代码题
  ├─ 判断当前面试阶段
  ├─ 生成受约束的问题
  └─ 调用评估器处理上一轮回答
       ↓
结果处理
  ├─ SSE 流式返回
  ├─ Judge0 代码执行结果
  ├─ Rubric 结构化评估
  ├─ Qdrant / Mem0 持久化
  └─ AI 请求指标记录
```

主要入口和实现文件：

| 模块 | 实现位置 | 作用 |
| --- | --- | --- |
| 请求入口 | `app/agent/chat_agent.py` | 组装记忆、会话历史和 AgentState |
| Agent 图 | `app/agent/langgraph_agent.py` | 定义状态、路由、SkillRunner 和结束边界 |
| Skill 注册 | `app/services/skill_registry.py` | 发现、注册和解析可用 Skill |
| 面试运行时 | `app/services/interview_skill.py` | 组织上下文、检索、阶段控制和问题生成 |
| 岗位知识库 | `app/services/role_knowledge_store.py` | Qdrant 岗位题库检索 |
| 代码题知识库 | `app/services/coding_knowledge_store.py` | Qdrant 代码题检索 |
| 回答评估 | `app/services/interview_evaluator.py` | 结构化 Rubric 评分和证据校验 |
| 代码执行 | `app/services/code_runner.py` | Judge0 代码运行适配 |
| 运行指标 | `app/services/metrics.py` | 保存请求成功率、耗时、Token 和成本 |

## 3. Agent Runtime 和状态控制

### 3.1 Skill 注册与路由

`SkillRegistry` 会扫描项目中的 `SKILL.md`，读取 Skill 名称、描述和触发词，并将其注册为可执行的 `SkillDefinition`。

当前面试 Skill 的执行过程是：

1. 请求携带 `skill_name` 或面试岗位参数。
2. `SkillRegistry` 解析出 `interview-skills`。
3. LangGraph 将请求交给 `SkillRunner`。
4. `InterviewSkillRunner` 调用 `InterviewSkill.run()`。
5. Skill 返回问题、评估结果和是否结束等结构化结果。

这使面试逻辑不需要散落在普通聊天逻辑中，也为后续注册其他 Skill 保留了扩展点。

### 3.2 AgentState

`AgentState` 保存以下运行时数据：

- `interview_role`、`interview_level`、`interview_type`：岗位、级别和面试轮次。
- `jd_content`、`resume_content`：岗位和候选人背景。
- `relevant_docs`、`context`：当前会话历史和上下文。
- `previous_interviewer_question`：上一轮面试官问题，用于评估当前回答。
- `code_execution`：Judge0 执行结果。
- `evaluation`：结构化评估结果。
- `iterations`、`max_iterations`、`is_finished`：流程边界和结束状态。

模型不是直接接收零散参数，而是接收经过统一状态组织的上下文。这是当前项目中上下文工程的主要落点。

### 3.3 防止流程漂移的实际方法

当前采用的是“规则门控 + 状态上下文 + Prompt 约束”的混合控制方式：

- 代码中限制面试题数量，达到轮次上限后直接结束。
- 提供系统结束指令，允许后端显式结束面试并生成报告。
- 根据面试轮次和已完成问题数量判断是否切换代码题。
- 通过代码特征识别判断用户输入是否为代码提交。
- 在 Prompt 中限制一次只问一个主问题，禁止输出题库栏目、报告格式和长篇答案。
- 将上一轮问题、历史回答和当前阶段传入模型，要求模型继续深挖而不是重新开始。

因此，模型主要负责生成自然语言，不负责单独决定所有流程边界。当前实现可以降低流程漂移，但不能保证模型在所有情况下绝不重复或偏题。

## 4. 上下文工程与检索链路

### 4.1 上下文来源

面试请求会组合以下上下文：

1. 用户级 Mem0 长期记忆。
2. 当前租户、用户和会话范围内的 Qdrant 历史问答。
3. `interview-skills` 下的 `SKILL.md` 和参考文档。
4. 岗位题库和岗位核心能力模型。
5. Qdrant 岗位知识库召回结果。
6. Qdrant 代码题知识库召回结果。
7. 当前 JD 和简历内容。
8. Judge0 代码执行结果。

`InterviewSkill` 会对 JD 和简历做规则化摘要，并提取候选人的项目、技术栈、成果和行动线索，再将这些内容注入面试 Prompt。

### 4.2 岗位知识检索

岗位知识库使用独立 Qdrant collection，文档包含岗位、题型、考察点、回答方向等元数据。

当前检索流程是：

1. 规范化岗位名称。
2. 构造由岗位、轮次、问题、JD 和简历组成的查询文本。
3. 使用岗位元数据过滤，避免检索到明显不相关的岗位题目。
4. 使用向量相似度召回 Top-K 文档。
5. 将题目、题型、考察点和回答方向拼接到 Prompt。

如果 Qdrant 不可用或没有返回结果，系统会回退到本地岗位题库和规则化岗位知识上下文。

### 4.3 代码题检索

代码题知识库使用独立 Qdrant collection，检索条件包含：

- 目标岗位或通用软件工程师岗位。
- 当前面试轮次。
- 由岗位、轮次和“手撕代码”组成的查询文本。

召回结果会携带题目、难度、输入输出要求、示例和评测重点。检索失败时回退到 `app/knowledge/coding_question_bank.json`。

当前没有实现以下高级检索能力：

- 难度字段的硬过滤。
- 独立的 Reranker 重排序模型。
- 相似度阈值拒答。
- 召回质量离线指标，例如 Recall@K、MRR 或 NDCG。

因此，项目文案应写成“元数据过滤 + 向量召回 + 本地回退”，不应写成“按岗位、轮次、题型和难度精确过滤并重排序”。

## 5. 动态问题生成与阶段策略

问题生成不是一个固定模板，而是由以下输入共同决定：

- 面试岗位和轮次。
- JD 中提取的要求。
- 简历中的项目和技术线索。
- 岗位题库的当前轮次重点。
- Qdrant 检索到的题目和考察点。
- 上一轮问题和候选人回答。
- 当前是否需要切换到代码题。

`InterviewSkill` 对不同阶段设置了策略：

- 一面优先验证岗位基础、原理和常见边界。
- 非一面开场优先引用简历中的具体经历。
- 项目问题要求继续追问职责、方案、指标、异常和取舍。
- 达到阶段条件后切换到代码题。
- 收到代码后优先追问复杂度、边界条件、线程安全和可维护性。

这里的“动态”主要来自规则计算出的阶段上下文与 LLM 生成结合，而不是由一个完全自主的 Agent 无限规划流程。

## 6. 工具调用与结果约束

### 6.1 SSE 流式响应

聊天接口通过 Server-Sent Events 返回模型输出，前端可以逐步展示生成结果。请求成功、失败和耗时会被记录到 AI 指标表中。

### 6.2 Judge0 代码执行

`Judge0CodeRunner` 将语言、源码和标准输入转换为 Judge0 请求，并处理：

- 不支持的语言校验。
- 请求超时。
- 上游请求异常。
- 编译输出、标准错误、运行状态、耗时和内存。
- 期望输出与实际输出的显式比较。

在评估阶段，如果 Judge0 返回编译错误、运行错误、超时、内存错误或错误答案，评估器会将代码正确性分数限制在较低范围，并把失败原因写入缺失项和错误分析。

## 7. 结构化评估 Harness

评估器使用 `with_structured_output(AnswerEvaluation)`，通过 Pydantic 定义评估 Schema，要求模型返回可校验的固定结构，而不是返回一段不可解析的自然语言。Pydantic Schema 是通用的工程实现方式，但不是面试评测领域唯一标准。

项目将 Rubric 定义为可版本化的评分配置，当前版本标记为 `rubric-v2`。`rubric-v2` 是本项目的内部版本，不是行业公认标准；它用于保证评分规则可追踪、可回归和可升级。

不同题型使用不同 Rubric：

- 技术原理题：技术正确性、原理深度、工程落地、表达结构。
- 项目深挖题：事实证据、个人贡献、技术深度、方案取舍、表达结构。
- 系统设计题：需求澄清、架构设计、可靠性取舍、落地方案、表达结构。
- 行为面试题：STAR 完整度、责任复盘、协作沟通、岗位动机、回答可信度。
- 代码题：算法选择、解法正确性、复杂度、边界条件、代码质量。

评估结果还包括：

- JD 要求匹配。
- 简历证据核对。
- 置信度分数和置信度等级。
- 正确性总结、错误分析、关键要点和修正建议。

系统会根据 Rubric 权重重新计算总分，而不是完全信任模型返回的 `overall_score`。这保证了不同题型可以使用不同评分标准。

## 8. 企业落地相关能力

### 8.1 数据隔离

- Mem0 使用租户和用户组合后的稳定作用域。
- Qdrant 会按 `tenant_id`、`user_id` 和 `chat_id` 过滤会话历史。
- 面试会话模型包含用户、租户和聊天 ID 的唯一约束。
- 回归测试覆盖不同租户和用户不能复用同一记忆范围。

### 8.2 超时、重试和降级

- Qdrant 连接异常时重建客户端并重试一次。
- Mem0 搜索和写入设置独立超时，失败时不阻塞主请求。
- Judge0 设置请求超时并转换为明确的 HTTP 错误。
- 岗位知识和代码题检索失败时回退到本地题库。
- 指标写入失败不会使面试请求失败。

### 8.3 可观测性

当前记录的 AI 请求指标包括：

- 用户和租户。
- 操作类型和模型。
- 请求成功状态。
- 延迟。
- 检索数量。
- 输入和输出 Token。
- 预估成本。

## 9. 测试与验证

当前仓库已经包含以下验证：

- `tests/test_ai_regression.py`：租户隔离、Qdrant 查询条件和 Skill 路由状态。
- `tests/test_interview_assessment.py`：题型识别、Rubric、分数边界和评估版本。
- `tests/evaluation_cases.json`：面试回答质量评估样例。
- `tests/evaluate_interview_quality.py`：批量计算评分误差和 verdict 准确率。

这些测试证明了部分核心组件可回归，但还不是完整的端到端评测平台。当前还缺少真实 LLM、Qdrant、Mem0 和 Judge0 全链路自动化测试，以及持续运行的召回质量和生成质量基线。

## 10. 当前边界与后续升级

为了避免项目介绍失真，当前应明确以下边界：

1. 面试阶段尚未拆成 JD 解析、简历解析、出题、追问、评估等多个独立 LangGraph 节点，部分阶段逻辑仍集中在 `InterviewSkill` 中。
2. `MemorySaver` 是进程内 Checkpointer，不适合作为多实例生产环境的持久化状态存储。
3. 检索链路还没有 Reranker、相似度阈值和离线 Recall@K 评测。
4. 题目生成目前仍由 LLM 结合策略上下文完成，尚未增加独立的重复题检测和事实引用校验器。
5. 当前质量评估脚本可以离线运行，但还没有接入 CI 门禁、实验追踪和 Trace 可视化平台。
