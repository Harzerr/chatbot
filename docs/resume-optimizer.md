# 简历优化模块

简历优化模块已经并入主项目的求职工作台，前端入口为 `/resume-optimizer`。它复用主项目的认证、SQLite/SQLAlchemy 数据库和 `/api/v1/career` API，不再启动原型目录中的独立 FastAPI 服务，也不直接读写共享 JSON 文件。

## 功能边界

- 原型的 `resume-profiles.json` 可以从 A4 编辑器导入。
- 导入内容会转换为当前登录用户的职业事实和教育档案；事实默认是“待确认”，确认后才能参与 AI 生成。
- 同一用户重复导入时，按“事实类型 + 标题”跳过重复记录，不会重复创建。
- 定制简历生成后，可在 A4 编辑器中编辑摘要、经历、项目、项目顺序和章节显示状态。
- 编辑保存到对应的 `resume_documents` 版本；PDF 导出继续使用后端 XeLaTeX 母版。

## API

- `POST /api/v1/career/profile/import`：导入原型 JSON。
- `PUT /api/v1/career/resumes/{resume_id}`：保存当前用户拥有的简历版本编辑。

所有接口都要求登录，并校验资源所属用户。原型 JSON 中的证件照、校徽和 HTML 只作为导入文件内容，不会直接写入服务端静态目录；生产环境应继续通过头像上传接口管理图片。

## 发布

修改前端或后端后，提交并推送到 `yql_dev`。GitHub Actions 在 runner 上完成前端构建，服务器只接收静态产物。后端发布时应沿用 systemd/Docker 的服务重启流程，不要在 2GB 服务器上运行 `npm run build`。

## 技术现状评估

| 领域 | 当前实现 | 产品化判断 | 主要问题 |
| --- | --- | --- | --- |
| 前端 | React + MUI，A4 在线编辑器，支持章节开关、项目排序和导出 | 已具备可用 Demo 到 MVP 的基础 | 编辑状态主要在浏览器内，缺少自动保存、撤销历史和多人协作能力 |
| 后端 | FastAPI + SQLAlchemy，复用认证、职业事实库、职位库和简历版本 | 具备模块化服务基础 | AI 生成、PDF 编译和网页抓取仍在请求链路中，慢任务可能阻塞接口 |
| 数据 | 当前使用 SQLite 和本地上传目录 | 适合单机验证 | 不适合多实例、高并发、灾备和跨服务器扩展 |
| AI | LLM 负责事实提取、JD 结构化和定制简历生成 | 已形成核心产品闭环 | 缺少严格结构化输出、模型版本记录、质量评测和失败重试 |
| 安全 | 登录鉴权、用户资源归属校验、导入事实默认待确认 | 基础安全边界存在 | 缺少限流、审计、敏感信息脱敏、文件安全扫描和更细的权限模型 |
| 部署 | 前端由 GitHub Actions 构建，服务器托管静态文件 | 方向符合企业实践 | 后端发布、数据库迁移、回滚、健康检查和告警还需要标准化 |

## 后续升级路线

下面按“先保证可用，再提升质量，最后扩展规模”的顺序规划。优先级中的 P0 应先完成，P1 是形成稳定产品的关键能力，P2 用于企业化和规模化。

| 优先级 | 技术升级项 | 建议落地方式 | 直接收益 | 验收指标 |
| --- | --- | --- | --- | --- |
| P0 | 异步任务队列 | 使用 Redis + Celery/RQ/Arq，将 JD 抓取、AI 生成、PDF 编译改成任务；API 返回 `task_id`，前端轮询或使用 SSE | 避免请求超时和后端内存峰值，提升弱服务器稳定性 | 95% 的生成请求在 2 秒内返回任务状态；任务失败可重试 |
| P0 | AI 输出强校验 | 为事实、JD、简历内容定义 Pydantic JSON Schema；使用结构化输出或 JSON 修复器，校验失败自动重试 | 防止模型输出缺字段、错类型或混入无依据内容 | 结构化输出通过率 ≥ 99%；无效结果不会写入正式版本 |
| P0 | 证据链与防幻觉 | 每个摘要、项目要点、技能和匹配结论必须携带 `fact_ids`；前端展示“来源事实”和“待确认”状态 | 让用户能核查每一句简历内容，降低虚构经历风险 | 生成内容 100% 可追溯；无来源文本禁止进入投递版 |
| P0 | 生成版本与审计 | 增加 `resume_revisions`、操作人、模型、Prompt 版本、输入事实快照、输出哈希和时间戳 | 支持撤销、对比、恢复和问题追责 | 任意版本可恢复；能还原一次生成的输入和输出 |
| P0 | 文件安全治理 | 限制文件大小和类型，校验真实 MIME，病毒扫描，随机化存储名；下载使用授权接口，不暴露物理路径 | 防止恶意文件、路径穿越和敏感文件泄露 | 非法格式拦截率 100%；用户只能访问自己的文件 |
| P0 | 运行可观测性 | 增加结构化日志、请求 ID、任务 ID、错误分类、耗时、Token 用量和 PDF 编译耗时 | 快速定位“生成慢、生成错、服务器崩溃”等问题 | 可按用户、任务和版本追踪完整链路；关键错误有告警 |
| P1 | PostgreSQL 数据库 | 从 SQLite 迁移到 PostgreSQL，使用 Alembic 管理迁移；JSON 字段按查询需求建立索引 | 支持并发写入、备份、读写扩展和多实例部署 | 数据库可恢复；迁移可重复执行；并发写入无锁库错误 |
| P1 | Redis 缓存与幂等 | 对职位 URL、JD 哈希、模型请求和 PDF 生成增加缓存；使用幂等键避免重复任务 | 降低 LLM、抓取和 PDF 编译成本 | 相同输入重复请求不重复消耗模型；缓存命中率可监控 |
| P1 | AI 质量评测集 | 建立脱敏简历/JD 样本集，评测事实准确率、关键词覆盖、证据覆盖、可读性和格式合法性 | 让模型升级从“凭感觉”变成可回归验证 | 每次模型或 Prompt 发布自动生成评测报告；关键指标不回退 |
| P1 | 模型路由与降级 | 简单任务使用低成本模型，复杂改写使用高质量模型；配置超时、重试、备用模型和熔断 | 控制成本并提升可用性 | 单模型故障时核心流程仍可用；单位简历成本可统计 |
| P1 | Prompt 与模型版本管理 | 将 Prompt、模型参数、Schema 作为版本化配置，随生成结果保存 | 支持 A/B 测试、回滚和问题复现 | 任意简历版本都能知道使用的模型和 Prompt 版本 |
| P1 | 个人资料与事实库增强 | 增加事实标签、有效期、来源文件、可信等级、去重向量和人工确认记录 | 提升长期复用和岗位匹配准确率 | 重复事实可合并；过期事实不会默认用于投递 |
| P1 | JD 解析鲁棒性 | 支持粘贴文本、公开 URL、PDF/DOCX；增加网页抓取超时、反爬提示和人工修正 | 降低职位导入失败率 | 常见 JD 格式解析成功率 ≥ 95%；失败时提供明确人工兜底 |
| P1 | 前端编辑体验 | 增加自动保存、草稿状态、撤销/重做、版本对比、快捷键和移动端降级布局 | 提升编辑效率，减少误操作丢稿 | 浏览器刷新后草稿可恢复；编辑操作可撤销 |
| P2 | 多租户与组织权限 | 引入组织、成员、角色、岗位项目空间和资源级 RBAC；所有查询带 tenant 条件 | 支持学校、企业招聘团队和 SaaS 化 | 跨租户访问测试 100% 拦截；管理员操作有审计 |
| P2 | 对象存储与 CDN | 将简历附件、头像、导出包放入 S3/OSS/COS，使用短时签名 URL | 支持多实例、备份和大文件访问 | 应用服务器无用户文件依赖；对象存储可独立备份 |
| P2 | 容器化与滚动发布 | GitHub Actions 执行测试、镜像构建、推送 Registry；服务器或 Kubernetes 拉取并滚动更新 | 发布可回滚，减少手工操作和环境漂移 | 发布失败自动停止；上一版本一键恢复 |
| P2 | 隐私与合规能力 | 敏感字段加密、日志脱敏、数据导出/删除、保留周期和用户授权记录 | 适配真实简历和企业数据合规要求 | 删除请求可验证完成；日志和备份不泄露手机号、邮箱等信息 |

## 推荐目标架构

| 层次 | 推荐组件 | 责任 |
| --- | --- | --- |
| Web 层 | Nginx/CDN + React 静态资源 | 页面、A4 编辑、任务状态展示和安全下载 |
| API 层 | FastAPI | 鉴权、参数校验、资源权限、任务提交和版本查询 |
| 任务层 | Redis + Worker | JD 抓取、事实提取、简历生成、PDF 编译和重试 |
| AI 层 | Model Gateway + Prompt/Schema Registry | 模型路由、超时、降级、Token 统计和输出校验 |
| 数据层 | PostgreSQL + Redis + 对象存储 | 业务数据、缓存/队列、附件和导出文件 |
| 质量层 | 评测集 + OpenTelemetry + Sentry/Prometheus | AI 回归、链路追踪、错误监控和容量预警 |
| 发布层 | GitHub Actions + Registry + systemd/Docker/Kubernetes | 测试、构建、部署、健康检查和回滚 |

## AI 产品质量指标

| 指标 | 定义 | 初期目标 |
| --- | --- | --- |
| 事实准确率 | 生成内容与已确认事实逐条比对的准确比例 | ≥ 98% |
| 证据覆盖率 | 简历要点中带有有效事实来源的比例 | 100% |
| JD 关键词覆盖率 | 适合候选人的关键词在简历中的合理覆盖比例 | ≥ 85%，且不强行补写缺失能力 |
| 生成成功率 | 任务在重试后返回可用结构化简历的比例 | ≥ 99% |
| P95 生成时延 | 从提交任务到得到可编辑版本的 95 分位耗时 | 异步化后 ≤ 60 秒 |
| PDF 成功率 | 生成内容成功编译为可下载 PDF 的比例 | ≥ 99.5% |
| 用户修改率 | 用户保存前主动修改 AI 内容的比例 | 作为体验观察指标，不追求越低越好 |
| 投递后反馈 | 用户对简历版本的收藏、下载、投递和面试反馈 | 作为后续推荐与评测数据来源 |

## 推荐实施顺序

| 阶段 | 建议内容 | 完成标志 |

| 第一阶段：稳定 MVP | 异步任务、Schema 校验、证据链、版本审计、日志和文件安全 | 服务器不因单次生成或 PDF 编译崩溃，生成结果可追溯 |
