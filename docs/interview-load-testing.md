# 面试系统压测方案与结果

## 1. 压测目标

本压测用于验证面试问答优化是否有效，重点不是直接宣称系统支持多少并发，而是测量以下指标：

压测是通过可控的并发用户、请求速率和持续时间模拟真实访问，测量系统在正常负载、峰值负载和超出容量后的延迟、吞吐、错误和资源表现。工业界通常将测试分为基准测试、负载测试、压力测试、突发测试、稳定性/Soak 测试和容量测试；本项目当前处于单机小规模负载/压力基线阶段，不等同于生产容量评估。

| 指标 | 定义 | 关注点 |
| --- | --- | --- |
| TTFT | 请求开始到收到第一段有效面试官文本 | 用户感知的首响应速度 |
| 完整响应时间 | 请求开始到 SSE 流结束 | 单次问答端到端耗时 |
| P50/P95 | 延迟中位数和尾部延迟 | 普通用户和慢请求体验 |
| 错误率 | HTTP 错误、超时、SSE 中断占比 | 稳定性 |
| 评估队列长度 | RQ 待处理任务数量 | 异步评估是否积压 |
| 后端 RSS | Uvicorn 进程常驻内存 | 是否存在内存持续增长 |

工业界压测通常同时关注以下指标：

- 用户体验：TTFT、首个完整句子时间、完整响应时间、流式中断率和重连次数。
- 延迟分布：平均值、P50、P95、P99；P95/P99 用于判断尾部慢请求。
- 吞吐：RPS、完成请求数、并发连接数和单位时间完成的业务流程数。
- 可靠性：HTTP 错误率、超时率、空 SSE 流、业务失败率、RQ 任务失败/重试率。
- 资源：CPU、RSS、可用内存、Swap、Load、连接数、文件描述符和事件循环阻塞。
- 异步任务：队列长度、等待时间、执行时间、失败数和排空时间。
- 下游与成本：LLM 延迟、Token、模型错误、Mem0/Qdrant/Judge0 耗时、限流和单次成本。

对于 SSE，HTTP 200 不能直接代表成功，至少要验证“收到有效内容”和“收到 `[DONE]`”。

## 2. 优化前后的链路

优化前，问答请求容易把问题生成、会话保存和评分逻辑耦合在同一条请求链路中：

```text
用户回答 → 问题生成 → 评估打分 → 保存结果 → 返回
```

优化后，核心问答和非核心评估分离：

```text
用户回答 → LangGraph / InterviewSkill → SSE 返回下一道问题
                                      └→ Redis + RQ Worker 异步评分
```

因此本次压测重点验证：问题是否能在评估完成前返回，以及评估任务是否进入 RQ 队列并最终完成。

## 3. 测试方法

### 3.1 测试环境

- 当前单台服务器部署 FastAPI、Redis、Qdrant 和相关 Agent 服务。
- FastAPI 使用单个 Uvicorn Worker。
- 压测请求发送到本机 `127.0.0.1:8000`，减少公网网络波动。
- 评估队列临时启动一个 `interview_evaluation` RQ Worker。
- 测试账号、密码通过命令行传入，不写入脚本和结果文件。

### 3.2 测试场景

`scenario` 模式包含两个阶段：

1. 使用唯一 `chat_id` 发起“开始面试”，测量首题生成。
2. 等待会话保存后提交一段较长回答，触发异步评估，测量下一题返回时间。
3. 读取 Redis 中 `interview_evaluation` 队列的前后状态。

### 3.3 并发策略

当前服务器只做小规模基线：

```text
1 并发 × 3 个场景
2 并发 × 3 个场景
5 并发 × 3 个场景
```

不在当前 2GB 级别服务器上直接进行 50 或 100 并发长连接压测，避免压测本身导致 OOM、Swap 抖动或影响其他服务。

## 4. 执行命令

先启动临时评估 Worker：

```bash
cd /srv/chatbot
source .venv/bin/activate
nohup rq worker interview_evaluation \
  --url redis://127.0.0.1:6379/1 \
  --logging_level INFO \
  > logs/interview-evaluation-load-worker.log 2>&1 &
echo $! > /tmp/interview-evaluation-load-worker.pid
```

执行压测：

```bash
python tests/benchmark_interview_sse.py \
  --username '测试账号' \
  --password '测试密码' \
  --requests 3 \
  --concurrency 2 \
  --mode scenario \
  --output reports/interview-sse-load-YYYYMMDD.json
```

停止临时 Worker：

```bash
kill "$(cat /tmp/interview-evaluation-load-worker.pid)"
```

### 5.1 本次实测结果（2026-08-13）

本次在当前单机环境执行 `2 并发 × 3 场景`，每个场景包含“开始面试”和“提交回答并触发评估”两个 SSE 请求，共 6 个请求。原始明细保存在 `reports/interview-sse-load-20260813.json`。

| 阶段 | 请求数 | 成功率 | TTFT 平均 | TTFT 范围 | 完整响应平均 | 完整响应范围 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 开始面试 | 3 | 100% | 18048ms | 16486–19707ms | 19861ms | 18276–21739ms |
| 提交回答并触发评估 | 3 | 100% | 8164ms | 7665–9020ms | 9432ms | 7831–10655ms |

资源和队列观察结果：

- 压测开始时评估队列待处理任务数为 `0`，5 秒观察窗口结束时为 `1`，说明提交回答后评估任务已经进入异步队列，但短时间内仍在消费。
- 继续观察约 35 秒后，队列待处理任务数回到 `0`，说明队列最终可以排空。
- Uvicorn RSS 从约 `49.56MB` 增长到 `113.50MB`；这是本次小样本过程中的进程内存变化，不代表长期内存泄漏结论。
- 6 个 SSE 请求全部成功，说明当前并发下主问答链路没有因为评估任务而返回 HTTP 错误。

### 5.2 多用户优化前后对比（2026-08-13）

为了实际量化优化效果，使用面试优化提交 `772f735` 的父版本作为优化前基线，当前 `yql_dev` 版本作为优化后版本。两次测试均使用 `6 个独立 chat_id`、`3 并发`、每个会话“开始面试 + 提交回答”两个 SSE 请求，共 `12 个请求`；账号、岗位、回答内容、服务器和模型配置保持一致。

原始数据：`reports/interview-sse-before-20260813.json`、`reports/interview-sse-after-20260813.json`。

本次数据不是估算值，而是由 `tests/benchmark_interview_sse.py` 在每个 SSE 请求中记录实际时间戳后计算得到。`ttft_ms` 表示从发送请求到收到第一段有效面试官文本的毫秒数。优化前总体平均值的计算方式为：

```text
优化前 12 次 TTFT 的平均值 = 61332.01ms ÷ 1000 = 61.33s
```

其中 12 次请求由 6 次“开始面试”和 6 次“提交回答并触发评估”组成：

| 阶段 | 请求数 | TTFT 平均 | TTFT P50 | TTFT P95 | 完整响应平均 | 完整响应 P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 优化前：开始面试 | 6 | 35.39s | 40.78s | 49.59s | 35.39s | 49.59s |
| 优化前：提交回答 | 6 | 87.28s | 97.05s | 111.51s | 87.28s | 111.51s |
| 优化后：开始面试 | 6 | 15.75s | 17.72s | 31.63s | 18.14s | 32.44s |
| 优化后：提交回答 | 6 | 10.96s | 11.54s | 14.04s | 13.50s | 21.54s |

| 指标 | 优化前 | 优化后 | 改善幅度 |
| --- | ---: | ---: | ---: |
| 总体 TTFT 平均 | 61.33s | 13.35s | 降低 78.2% |
| 总体完整响应平均 | 61.33s | 15.82s | 降低 74.2% |
| 提交回答 TTFT 平均 | 87.28s | 10.96s | 降低 87.4% |
| 提交回答完整响应 P95 | 111.51s | 21.54s | 降低 80.7% |
| SSE 请求成功率 | 100%（12/12） | 100%（12/12） | 保持稳定 |

结果说明：优化前，提交回答请求需要同步完成下一道问题生成和回答评估，3 个并发会话会互相争用单 Worker 和模型调用链路；优化后，主请求只负责生成下一道问题，评估请求通过 Redis + RQ 投递到 `interview_evaluation` 队列，评分在 Worker 中异步完成。因此用户提交回答后可以先收到下一道问题，评估延迟不再阻塞 SSE 主链路。

队列证据：优化前本次测试没有新增待处理评估任务；优化后观察窗口内出现 `queued=2、started=1`，证明评估任务已经从请求线程转移到 RQ Worker。测试结束后应继续观察队列是否排空，队列长期增长则说明 Worker 数量或评估耗时需要继续优化。

本轮资源 RSS 不作为前后结论：初次采集时优化前后两个 Uvicorn 进程同时存在，旧脚本会把两个进程相加。已修复 `tests/benchmark_interview_sse.py`，后续按目标 URL 端口单独统计 RSS。

### 5.3 递增多用户压力测试（2026-08-13）

考虑服务器总内存约 `1.9GiB`、Swap 已使用约 `1.1GiB`，且当前为单个 Uvicorn Worker 和一个 RQ Worker，本次没有直接执行 20、50 或 100 并发，而是采用递增策略：先完成已有的 `6 用户/3 并发` 对比，再增加到 `12 用户/4 并发`；当可用内存接近安全阈值且业务失败率升高时停止。

| 场景 | 用户数 | 并发 | 有效请求数 | 成功请求数 | 业务成功率 | TTFT 平均 | TTFT P95 | 完整响应平均 | 后端 RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 优化后基线 | 6 | 3 | 12 | 12 | 100% | 13.35s | 31.63s | 15.82s | 约 139.55MB → 约 496.64MB* |
| 递增压力 | 12 | 4 | 19 | 14 | 73.7% | 20.09s | 40.40s | 22.65s | 约 139.55MB → 约 338.28MB |

`12 用户/4 并发` 实际发起了 12 个开场请求；其中部分开场没有产出有效内容，因此没有继续产生对应的第二个请求，最终记录 19 个请求。5 个请求虽然 HTTP 状态为 200，但 SSE 内容为空，按业务失败计入失败率。已在 `tests/benchmark_interview_sse.py` 中增加 `empty_sse_stream` 分类，避免只看 HTTP 状态码。

压测过程中可用内存最低约 `368MB`，结束后约 `484MB`；后端进程 RSS 最高约 `338MB`，RQ Worker 子进程约 `329MB`。同时评估队列出现 `queued=2、started=1`，并持续产生结构化 JSON 长度超限失败。基于内存、空流失败和评估队列积压三个信号，本轮停止继续增加用户数；这不是“系统最多支持 12 用户”的容量结论，而是当前单机环境下的安全压力边界。

原始结果：`reports/interview-sse-after-12users-20260813.json`。

### 5.4 压测发现的评估问题

RQ Worker 的失败任务中出现：

```text
openai.LengthFinishReasonError: Could not parse response content as the length limit was reached
```

原因是评估模型在 `EVALUATION_LLM_MAX_TOKENS=1536` 时没有在输出上限内完成结构化评估 JSON。它没有阻塞本次 SSE 问答，但会导致后台评分失败，因此后续应增加结构化输出压缩、字段长度限制、重试或提高评估 token 预算。

本轮队列失败数由 `12` 增加到 `15`，同时有任务处于 `started`，日志还出现了 RQ `Task exceeded maximum timeout value (120 seconds)`。这说明评估 Worker 仍存在模型结构化输出超限和超时问题，需要单独优化评估任务的 token 上限、输出压缩、超时重试和失败降级。

这说明本次压测不仅验证了异步解耦效果，也发现了一个真实的后台评估可靠性问题。日报中应分别记录：主问答成功率为 100%，评估任务仍存在结构化输出失败和超时，不能把两者混为一个成功率。

## 6. 结果解读

- 多用户场景下总体 TTFT 平均从 `61.33s` 降到 `13.35s`，降低 `78.2%`；提交回答阶段的 TTFT 平均降低 `87.4%`，说明本次异步评估解耦确实改善了用户等待。
- 完整响应平均降低 `74.2%`，但仍受问题生成模型、Mem0、Qdrant 和网络波动影响，不能把全部收益归因于单一组件。
- 问答接口已经返回、但评估仍处于 `queued` 或 `processing`，说明主链路和评估链路已经解耦。
- 队列持续增长说明 Worker 数量不足或评估模型耗时过高，应扩展 Worker 或降低单任务成本。
- RSS 持续增长且不回落，需要进一步排查对象缓存、连接池和后台任务生命周期。
- 本轮对比是同机同参数的小样本基线，足以验证回归和优化方向，但不能直接推导生产级容量；递增压力测试的 12 用户结果说明当前瓶颈已经从主请求等待转移到模型并发、Worker 内存、空 SSE 流和评估队列处理能力。

## 7. 面试表达

> 我没有直接用普通 HTTP 压测，而是针对面试系统的 SSE 长连接设计了专门脚本，分别记录首字节时间、完整响应时间、P50/P95、错误率、RQ 队列长度和后端 RSS。测试场景先发起面试，再提交回答触发评估，用唯一 chat_id 隔离每个测试会话。通过比较问答接口返回时间和评估任务完成时间，验证评分是否已经从主请求中解耦。小规模压测只能证明当前单机下的性能回归和异步链路有效，不能直接推导生产级并发容量。

## 8. 限制

- 当前服务器配置较小，结果只代表单机小规模基线。
- LLM、Qdrant、Redis 和 Judge0 的网络及服务状态会影响延迟。
- 本轮已有同条件父版本基线，但仍应通过多轮重复测试和置信区间降低外部模型波动带来的误差。
- 如果要继续扩大并发，应先增加 Worker/服务实例、独立压测机和监控，再执行 20/50/100 用户的阶梯压测；否则压测机、业务服务和 LLM 客户端会争用同一台服务器资源。
- 生产容量评估需要独立压测机、分布式负载生成器和多实例服务部署。
