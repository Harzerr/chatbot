## 面试提问与评估 Token/耗时可观测性

### 1. 动机

之前只能通过压测脚本统计 SSE 的 TTFT，无法区分“提问模型耗时”“评估模型耗时”和“评估在队列中等待的时间”。提问侧的 Token 字段长期为 `0`，评估侧也没有输入、输出 Token 记录，因此无法真实比较优化前后的模型成本。

### 2. 实现方式

| 链路 | 采集内容 | 实现方法 |
| --- | --- | --- |
| 提问 | 输入 Token、输出 Token、总 Token、模型耗时、请求总耗时 | `InterviewSkill` 在普通调用读取 `AIMessage` usage；流式调用读取开启 `stream_usage` 后的末块，并用最大值合并，避免把每个流式 chunk 重复累加。 |
| 评估 | 主评估和紧凑重试的 Token、模型耗时、调用次数 | `InterviewEvaluator._invoke_json` 在每次模型调用前后记录耗时，并累计响应中的 `usage_metadata` 或 `response_metadata.token_usage`。主请求失败后，紧凑重试也会被纳入总量。 |
| 队列 | RQ 排队等待时间 | 提交任务时写入 `queued_at`，Worker 启动后计算到实际执行的等待时间。 |
| 缓存 | 评估缓存命中次数 | 缓存命中仍记录一条指标，但 Token 和模型耗时为 `0`，并标记 `cache_hit=1`。 |
| 汇总 | 按 `interview_question`、`interview_evaluation`、`chat` 分组 | `/api/v1/metrics/summary` 新增 `by_operation`，分别返回请求数、平均请求耗时、平均模型耗时、平均队列等待、输入/输出/总 Token 和缓存命中数。 |

新增字段包括 `model_latency_ms`、`queue_wait_ms`、`total_tokens`、`cache_hit` 和 `attempt`，应用启动时通过数据库 bootstrap 自动补齐旧 SQLite 表结构。

### 3. 统计口径

- `latency_ms`：从业务调用开始到业务调用结束的总耗时。
- `model_latency_ms`：实际等待远程模型响应的耗时，不包含 RAG、数据库和队列等待。
- `queue_wait_ms`：评估任务进入 Redis/RQ 后，到 Worker 开始处理前的等待时间。
- `prompt_tokens`、`completion_tokens`：优先读取供应商返回的真实 usage，不再使用“字符数除以 4”的估算。
- 如果供应商没有返回 usage，记录为 `0`，不能将其解释为模型实际消耗了 0 Token；需要通过监控中的非零覆盖率识别采集缺失。

### 4. 验证结果

- 新增 `tests/test_llm_usage.py`，验证 LangChain 两种 usage 格式、流式 chunk 去重合并和评估调用次数统计。
- 评估队列、缓存、失败隔离和回归测试通过；全量测试结果为 `59 tests OK`。
- 后端重启后已确认 `ai_request_metrics` 新字段完成迁移，评估 Worker 已加载新代码。
- 当前历史 `113` 条面试指标中的 Token 仍为 `0`，因为它们产生于采集改造之前或供应商未返回 usage，不能回填为真实值。下一次真实面试或压测产生的新记录，才可用于前后 Token 成本对比。

### 5. 与已有压测结果的关系

已有多用户压测已经证明用户等待时间改善：总体 TTFT 从 `61.33s` 降至 `13.35s`，提交回答阶段从 `87.28s` 降至 `10.96s`。这主要来自评估异步化，不能直接等同于模型 Token 或模型推理耗时下降。完成一次新压测后，应同时比较 `by_operation.interview_question` 和 `by_operation.interview_evaluation`，再报告真实 Token、P50/P95、队列等待和缓存命中率变化。

## 技术文档证据链修正

### 1. Prompt 增量口径

当前职业事实 RAG 只在项目经历、实习经历等项目深挖问题中启用，代码题和基础题不会拼接职业事实。提问 Prompt 最多增加约 `3200` 个字符，评估主请求最多增加约 `3000` 个字符，紧凑重试最多增加约 `1200` 个字符；这些是字符预算，不是实际 Token。真实 Token 以模型返回的 usage 为准，历史记录尚未采集到真实 usage，不能回填推算。

对当前用户已保存的 `5` 份技术文档进行本地实测：项目/实习查询召回上下文约 `843–1065` 字符，按“字符数 ÷ 4”仅作粗略估算约增加 `211–266` 个输入 Token；同一回答会同时影响提问和评估，因此单轮两次调用的估算增量约 `422–532` 个输入 Token。RAG 本地切块、排序和拼接 `30` 次测试平均约 `7.6ms`，这不包含远程模型因输入变长而增加的推理时间。代码题样本不会启用职业事实召回。

### 2. 证据来源修正

之前的链路是：RAG 切片进入 Prompt，模型可能输出 `knowledge_evidence`；如果模型没有输出，报告聚合层就会使用“作答摘录（待核验）”作为兜底。因此报告中的证据并不总是 RAG 切片。

现在评估器会从同一份 Evidence Pack 中确定性提取完整的 `[证据ID｜职业事实｜文档｜章节]` 和切片正文，写入 `knowledge_evidence`，同时保存 `knowledge_evidence_ids` 和 `knowledge_evidence_source=career_rag`。这样项目经历/实习经历的报告优先展示 RAG 召回证据；候选人回答仍作为独立的作答证据，不能冒充项目事实证明。

## 企业级证据链加固

### 1. 这次改造针对的问题

当前系统已经把技术文档放入提问和评估 Prompt，但仅把文本拼进 Prompt 仍然存在三个生产风险：

1. 长段 Markdown 直接按固定长度截断，可能把一个关键实现步骤切在两个片段之间，导致模型只看到半个证据。
2. 旧版本 Evidence Header 没有版本号和检索分数，报告只能显示文本，无法回答“这条证据来自哪个文档版本、为什么被召回”。
3. 只记录普通会话的 `retrieval_count`，无法区分历史对话召回和职业技术文档召回，也无法量化文档上下文带来的 Token、缓存和延迟影响。

### 2. 设计思路

采用“有界检索 + 稳定证据 ID + 证据门控 + 指标审计”的方式，而不是把用户全部文档直接交给 LLM：

| 层次 | 实现 | 目的 |
| --- | --- | --- |
| 文档层 | Markdown 按标题和段落切分，长段使用 `120` 字符重叠窗口 | 保留跨块的上下文，避免关键句在边界处丢失 |
| 检索层 | 词法 BM25 风格打分、标题/章节加权、最低分阈值、每文档最多 `2` 个切片 | 先过滤无关文档，控制 Prompt 大小，避免低相关资料污染判断 |
| 证据层 | 生成 `evidence_id`、文档 ID、事实 ID、章节、源版本 Hash、检索分数和原文引用 | 评估结果可回溯、可复核、可审计 |
| 评估层 | 评估器从同一份 Evidence Pack 确定性回填证据；无证据时只能输出“证据不足” | 防止模型自行编造项目证明，区分候选人自述和用户上传资料 |
| 缓存层 | Redis Key 包含检索器版本、用户/租户、查询、文档版本、切块参数和阈值 | 文档编辑或算法升级后自动失效，避免读到旧证据 |
| 观测层 | 新增证据召回数、上下文字符数、缓存命中、检索方法四项指标 | 能单独计算 RAG 增量，而不是把它混在普通历史检索中 |

### 3. 关键实现位置

- `app/services/career_knowledge.py`：切块重叠、检索阈值、证据 Pack、缓存 Key 和安全统计函数。
- `app/schemas/chat.py`：新增 `EvidenceItem`，保存来源类型、核验状态、原文引用、文档版本和检索分数。
- `app/services/interview_evaluator.py`：兼容旧 Header，并从新旧格式统一解析结构化证据。
- `app/services/interview_report.py`：优先展示 RAG 证据；只有没有 RAG 证据时，才展示“作答摘录（待核验）”。
- `app/models/ai_metrics.py`、`app/db/bootstrap.py`、`app/agent/chat_agent.py`、`app/services/evaluation_jobs.py`：记录提问和评估两条链路的证据召回指标；旧 SQLite 表由启动迁移自动补字段。

### 4. 验证与结果

- 新增长文本重叠切块测试、结构化/旧版证据 Header 兼容测试和证据统计脱敏测试。
- 职业知识测试 `11` 项通过；评估和 Token 测试 `31` 项通过；全量单元测试 `62 tests OK`。
- 后端重启后确认 `ai_request_metrics` 已存在 `evidence_retrieval_count`、`evidence_context_chars`、`evidence_cache_hit`、`evidence_retrieval_method` 四个字段。
- 统计函数只保存数量、字符数和方法名，不保存技术文档原文，避免观测系统反向扩大敏感数据暴露面。
- 当前实现的检索器是轻量、可降级的词法召回；它适合当前单机和小规模用户。真正规模化部署时，下一阶段应增加异步向量索引、稠密+稀疏混合召回、Reranker 和离线 Golden Set 评测，不能把当前方案表述成已经完成的向量混合检索。

### 5. 生产验收指标

上线后按 `interview_question` 和 `interview_evaluation` 分组观察：

- `evidence_retrieval_count`：平均每次调用实际注入的证据切片数。
- `evidence_context_chars`：注入 Prompt 的技术资料字符预算，用于估算 Token 增量并和真实 provider usage 对账。
- `evidence_cache_hit`：Redis 复用次数，用于识别重复检索和降低本地检索开销。
- `prompt_tokens`、`model_latency_ms`、`queue_wait_ms`：分别衡量上下文成本、模型耗时和异步排队耗时。

验收不能只看“模型回答是否成功”，还要同时检查证据命中率、证据可回溯率、无关问题的误召回率、P95 延迟和评估失败率。

## 企业级检索增强：异步向量索引与混合召回

### 1. 增强动机

词法召回对“Redis 队列”和“Redis 后台任务”这类词面接近的问题有效，但对同义表达、缩写和中文自然语言改写不稳定；如果在请求线程内实时生成 Embedding，还会把远程 Embedding 延迟叠加到面试提问和评估链路。因此本次增加向量索引，但不让向量服务成为强依赖。

### 2. 实现方案

```text
上传/编辑 Markdown
  -> 保存 CareerKnowledgeDocument
  -> RQ career_evidence_index 队列
  -> Worker 按文档版本切块并生成 Embedding
  -> Qdrant career_evidence 集合
  -> 面试请求先执行词法召回
  -> 同租户/同用户/可选 fact_id 的向量召回
  -> Reciprocal Rank Fusion 混合排序
  -> Evidence Pack + Redis 缓存
  -> 提问与评估复用同一份证据
```

关键设计：

- `CareerEvidenceVectorStore` 使用 `tenant_id + user_id + document_id + chunk_id + source_hash` 生成确定性 Point ID，重复索引不会无限产生脏点。
- Qdrant 查询强制包含租户和用户过滤条件，项目事实通过 `fact_id` 进一步隔离，不能跨用户召回技术文档。
- 混合排序使用 RRF：词法和语义分别按排名贡献分数，默认权重为 `0.55 / 0.45`；语义分数不足的结果不会进入 Evidence Pack。
- 上传、编辑、归档只负责写数据库并投递索引任务，不等待 Embedding；队列失败或 Qdrant 不可用时，主链路自动退回词法召回。
- `scripts/reindex_career_evidence.py` 用于首次启用、模型更换或索引损坏后的全量重建。

### 3. 开关与上线方式

当前默认 `CAREER_EVIDENCE_VECTOR_ENABLED=false`，这是为了保护现有单机环境和避免未完成索引时突然增加远程 Embedding 成本。灰度上线时：

1. 在 `.env` 设置 `CAREER_EVIDENCE_VECTOR_ENABLED=true`。
2. 重启 `resume_worker`，使其监听 `career_evidence_index` 队列。
3. 执行 `./.venv/bin/python scripts/reindex_career_evidence.py`，等待历史文档建索引。
4. 通过指标观察 `retrieval_method=hybrid_rrf` 的占比、P95 延迟、Embedding 失败率和词法回退率。
5. 只有在混合召回的相关性和稳定性达到验收标准后，才扩大用户范围。

### 4. 本次验证

- 向量索引单元测试验证了稳定 Point ID、租户/用户元数据、文档版本和来源信息。
- 混合召回测试验证了语义排名参与排序；Qdrant 异常测试验证自动回退到 `lexical_bm25_heading_boost`。
- 职业知识测试 `13` 项、向量索引/评估测试 `33` 项、全量单元测试 `64 tests OK`。
- 本次没有打开生产向量开关，因此没有对当前用户产生额外 Embedding 请求；真实启用后的收益必须用线上 `prompt_tokens`、`model_latency_ms`、`evidence_cache_hit` 和召回质量 Golden Set 重新测量。

## 评估入口与证据人工核验

### 1. 用户侧改动

原先面试结束后的按钮直接执行“导出报告”，用户无法先查看评估过程，也无法判断职业事实召回是否真的支持评分。本次将入口改为“进行评估”，跳转到 `/chat/{chat_id}/evaluation` 独立页面；页面展示综合结论、分维度得分、优势、改进项和逐题评估，同时保留“导出评估报告”。

### 2. 证据反馈链路

```text
评估页面加载报告
  -> 展示每题的 knowledge_evidence_items
  -> 用户标记正确 / 不正确 / 部分相关
  -> 对错误或部分相关证据补充说明
  -> POST evidence-feedback
  -> 校验 evidence_id 属于当前题目
  -> 写回 Qdrant 会话 metadata
  -> force_refresh=true 投递 interview_evaluation 队列
  -> EvaluationAgent 将反馈作为纠偏上下文重新评估
  -> 页面轮询 queued/processing/completed 状态
```

反馈不是直接改分，而是受控输入：后端只接受当前题目已有的证据 ID，避免客户端伪造跨用户证据；重新评估强制绕过旧 Redis 评估缓存，防止反馈提交后继续返回旧结果。用户反馈同时保存到会话 metadata，报告接口会原样返回，便于复核和审计。

### 3. 验证

- 后端新增反馈请求 Schema、缓存 Key 差异和报告回传测试。
- `python3 -m compileall -q app` 通过；虚拟环境下确认接口注册为 `POST /api/v1/history/chats/{chat_id}/messages/{point_id}/evaluation/evidence-feedback`。
- `npm run build` 通过；仅保留仓库原有 Hook 依赖、未使用变量和 BOM 警告，无新增编译错误。

### 4. 评估页展示口径
