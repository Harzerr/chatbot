# 2026-08-13 工作日报

## 一、面试问答多用户压测与优化效果验证

### 1. 目标

验证面试问答链路从“同步评估”改为“问答与评估解耦”后，是否真正改善多用户场景下的等待时间，而不是只根据单次请求或主观感受判断优化效果。

### 2. 什么是压测

压测是通过可控的并发用户、请求速率和持续时间，模拟真实用户访问，观察系统在正常负载、峰值负载和超过容量后的响应能力。压测不等于简单地发送很多 HTTP 请求，而是要同时验证用户场景、依赖服务、资源消耗、错误类型和恢复能力。

工业界通常会区分以下测试类型：

| 类型 | 目的 | 本项目的对应场景 |
| --- | --- | --- |
| 基准测试 | 在固定低并发下建立可重复基线 | 1–3 个并发会话，比较优化前后 TTFT |
| 负载测试 | 验证预期并发下的稳定性 | 多个用户同时开始面试并提交回答 |
| 压力测试 | 逐步超过预期负载，寻找系统拐点 | 从 3 并发递增到 4 并发，观察错误率和内存 |
| 突发测试 | 模拟短时间大量用户同时进入 | 多个会话同一时间发起开场请求 |
| 稳定性/Soak 测试 | 观察长时间运行是否泄漏或积压 | 长时间 SSE、RQ 队列和 RSS 变化 |
| 容量测试 | 找到满足目标 SLO 的最大并发 | 需要独立压测机和生产规模部署后执行 |

工业界不会只看“接口返回 200”。本项目重点观察：

- **用户体验指标**：SSE `TTFT`、首个完整句子时间、完整响应时间、流式中断率和重连次数。
- **延迟分布**：平均值用于总体趋势，P50 代表典型用户，P95/P99 代表尾部慢请求；面试场景不能只看平均值。
- **吞吐指标**：请求数、完成请求数、每秒完成请求数、并发连接数和单位时间完成的面试轮次。
- **可靠性指标**：HTTP 错误率、超时率、空 SSE 流、业务失败率、RQ 任务失败率和任务重试率。
- **资源指标**：CPU、RSS、可用内存、Swap、Load、文件描述符、连接数和事件循环阻塞情况。
- **异步链路指标**：队列长度、任务等待时间、任务执行时间、成功/失败/超时数量和队列排空时间。
- **下游依赖指标**：LLM 延迟和 Token、Mem0/Qdrant/Judge0 请求耗时、连接超时和限流次数。
- **成本与容量指标**：单次问答 Token、单次评估成本、Worker 消费能力以及在目标 SLO 下可承载的并发数。

本项目使用 SSE，因此还要区分三种结果：HTTP 返回成功、SSE 收到首段内容、SSE 正常发送 `[DONE]`。本轮发现的 HTTP 200 但空 SSE 流，说明只看 HTTP 成功率会漏掉真实用户失败。

### 3. 压测设计

针对项目使用 SSE 流式问答的特点，编写 `tests/benchmark_interview_sse.py`，记录以下指标：

- `TTFT`：从发送请求到收到第一段有效面试官文本的时间，代表用户首次可感知响应速度。
- 完整响应时间：从发送请求到 SSE 流结束的时间。
- 成功率：HTTP 错误、超时或 SSE 中断的请求比例。
- P50/P95：分别观察典型用户和慢请求的延迟。
- RQ 队列状态：记录评估任务的 `queued`、`started`、`failed` 和 `finished` 数量。
- 后端 RSS：观察 Uvicorn 进程的内存占用。

压测场景采用 6 个独立 `chat_id` 模拟 6 个用户，并发数设置为 3。每个用户依次执行：

```text
开始面试 → 获取第一道问题
提交回答 → 获取下一道问题，同时触发后台评估
```

为了保证前后结果可比较，优化前使用面试优化提交 `772f735` 的父版本 `6427123`，优化后使用当前 `yql_dev` 版本。两次测试使用相同账号、岗位、回答内容、模型配置、服务器和并发参数，共产生 12 个 SSE 请求。

### 4. 实现方式

优化前，候选人提交回答后，后端在同一条请求链路中执行下一道问题生成和评估：

```text
提交回答 → 读取上下文 → 生成下一题 → LLM 结构化评估 → 保存评估 → SSE 返回
```

评估模型耗时较长时，会直接阻塞主请求；多个用户同时提交回答时，还会争用单个 Uvicorn Worker 和模型调用资源。

优化后，在 `app/services/interview_skill.py` 中只构造 `EvaluationRequest`，不再同步等待评估结果；`app/agent/chat_agent.py` 在问答结果保存后，将评估任务投递到 Redis 队列：

```text
提交回答 → 生成下一题 → SSE 返回
                 └→ Redis → interview_evaluation RQ Worker → EvaluationAgent → 更新评估结果
```

具体实现包括：

1. `app/services/task_queue.py` 增加 `get_evaluation_queue` 和 `enqueue_evaluation_job`，统一封装 Redis 连接、队列名称、超时和任务生命周期。
2. `app/services/evaluation_jobs.py` 增加 RQ 任务入口，在 Worker 中调用 `EvaluationAgent`，并将评估状态更新为 `processing`、`completed` 或 `failed`。
3. `app/workers/resume_worker.py` 注册 `interview_evaluation` 队列，使现有 Worker 可以消费评估任务。
4. `app/agent/chat_agent.py` 先保存问答记录，再使用问答记录的 point ID 绑定评估任务，避免评估结果无法回写到原始回答。
5. `app/services/streaming.py` 使用队列接收模型输出，保证 SSE 可以持续向前端发送内容，并避免重复发送已流式返回的文本。

### 5. 实测结果

原始结果保存于：

- `reports/interview-sse-before-20260813.json`
- `reports/interview-sse-after-20260813.json`

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 总体 TTFT 平均 | 61.33s | 13.35s | 降低 78.2% |
| 总体完整响应平均 | 61.33s | 15.82s | 降低 74.2% |
| 提交回答 TTFT 平均 | 87.28s | 10.96s | 降低 87.4% |
| 提交回答完整响应 P95 | 111.51s | 21.54s | 降低 80.7% |
| SSE 请求成功率 | 12/12，100% | 12/12，100% | 保持稳定 |

TTFT 的计算不是估算值，而是脚本在每个 SSE 请求中记录发送时间和第一段有效内容到达时间后计算：

```text
优化前 12 次 TTFT 平均值 = 61332.01ms ÷ 1000 = 61.33s
```

本次优化的主要效果是：用户提交回答后，不需要等待后台评分完成即可先看到下一道问题。评估任务进入 RQ 队列，主问答链路和评估链路实现了时间上的解耦。

### 6. 递增压力测试结果

考虑当前服务器总内存约 `1.9GiB`、Swap 已使用约 `1.1GiB`，并且只运行单个 Uvicorn Worker 和一个 RQ Worker，没有直接执行 20、50 或 100 用户，而是采用逐级加压：先完成 `6 用户/3 并发` 对比，再增加到 `12 用户/4 并发`，同时监控可用内存、RSS、空 SSE 流和评估队列。

| 场景 | 用户数 | 并发 | 记录请求数 | 成功请求数 | 业务成功率 | TTFT 平均 | TTFT P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 优化后基线 | 6 | 3 | 12 | 12 | 100% | 13.35s | 31.63s |
| 递增压力 | 12 | 4 | 19 | 14 | 73.7% | 20.09s | 40.40s |

`12 用户/4 并发` 中有 5 个请求返回 HTTP 200，但没有收到有效 SSE 内容，因此按业务失败统计；由于这些开场请求没有产出问题，对应会话没有继续发起第二个请求。压测过程中可用内存最低约 `368MB`，后端 RSS 最高约 `338MB`，RQ Worker 子进程约 `329MB`，评估队列出现 `queued=2、started=1`。基于内存下降、空 SSE 流和评估任务积压三个信号，本次停止继续增加并发。

这不是“系统最多支持 12 用户”的容量结论，而是当前单机环境的安全压力边界。要继续执行 20/50/100 用户压测，应先扩展 Worker 或服务实例、使用独立压测机并接入 CPU、内存、Swap、队列和下游 LLM 监控，否则压测流量会和业务服务争用同一台服务器资源。原始结果见 `reports/interview-sse-after-12users-20260813.json`。

### 7. 压测中发现的问题与处理

#### 问题一：初始基线服务无法启动

临时启动父版本时，旧版本初始化 OpenAI 客户端读取到了当前 shell 的 SOCKS 代理环境，但虚拟环境没有安装 `socksio`，导致服务启动失败。

处理方式：

- 清理临时压测进程的 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 环境变量。
- 使用独立 worktree 启动父版本，监听 `18000` 端口。
- 当前版本继续监听 `8000` 端口，避免修改线上服务。

#### 问题二：父版本使用了不同的 SQLite 文件

临时 worktree 启动后自动创建了新的 `app.db`，测试账号不存在，导致登录返回 401。排查登录接口后确认认证逻辑没有变化，真正原因是父版本使用了空数据库。

处理方式：将临时 worktree 的数据库链接到当前项目的 `app.db`，保证前后版本使用同一份测试数据，同时每个压测会话使用唯一 `chat_id` 避免历史消息互相污染。

#### 问题三：RSS 初始统计口径不准确

前后版本同时运行时，旧版脚本只按 `uvicorn app.main:app` 匹配进程，会把 `8000` 和 `18000` 两个服务的内存相加，导致 RSS 不能用于前后比较。

处理方式：在 `tests/benchmark_interview_sse.py` 中解析 `base_url` 端口，只统计目标端口对应的 Uvicorn 进程。本轮 RSS 数据不作为优化效果结论，后续单独运行服务时再采集。

#### 问题四：评估任务仍有结构化输出失败和超时

主问答 SSE 成功率为 100%，但 RQ Worker 日志发现：

- `openai.LengthFinishReasonError`：此前评估模型输出达到 `EVALUATION_LLM_MAX_TOKENS=1536`，没有完成结构化 JSON；本次将上限收紧到 1024，并增加字段级长度约束。
- `rq.timeouts.JobTimeoutException`：评估任务超过 RQ 的 120 秒任务超时。

这说明异步化解决了“评估阻塞用户问答”的问题，但没有自动解决“评估任务本身可靠完成”的问题。后续需要继续做评估输出压缩、字段长度限制、结构化 JSON 重试、任务超时降级和失败状态补偿，问答成功率与评估成功率也要分开统计。

本次进一步增加协程硬超时和规则降级：远程模型主请求与紧凑请求各最多等待 20 秒，仍未返回时使用保守 Rubric 规则生成临时结果，并标记 `evaluation_mode=fallback`、低置信度。真实重试最新失败任务验证：远程请求未在 40 秒内完成，但任务最终以 `completed` 写回，不再因 RQ 180 秒超时停留在 `failed`。

压测完整方案和结果见 `docs/interview-load-testing.md`。

## 二、上传 Markdown 提炼项目经历并新增 Resume Optimizer Skill

### 1. 目标

在职业事实库中新建项目事实时，允许用户上传项目技术文档或项目复盘 Markdown，由 AI 提炼为一条完整、可核查、可编辑的项目经历草稿。目标不是简单摘要，而是把项目标题、角色、技术栈、工作内容、结果和证据组织成适合技术简历的结构化事实。

### 2. 为什么新增独立 Skill

原有 `interview-skills` 的职责是模拟面试、生成问题和控制面试轮次。如果直接把简历提炼规则塞入该 Skill，会导致面试流程和简历事实抽取耦合，后续修改一方可能影响另一方。

因此新增独立目录 `resume-optimizer-skill/SKILL.md`，明确边界：

```text
Resume Optimizer Skill：Markdown/项目文档 → 结构化职业事实 → 人工确认
Interview Skill：职业事实/JD/对话上下文 → 面试问题和追问
```

`app/services/skill_registry.py` 负责发现并注册 Skill；`CareerStudioService` 直接加载 `resume-optimizer-skill/SKILL.md`，只在 Markdown 事实提炼时使用，不把它注册成面试 Agent，也不改变原有 `interview-skills` 的流程状态机。

### 3. 工业界编写 Skill 的常见规范

Skill 不应只是几段 Prompt，而应当是一个有明确边界、输入输出契约和质量门禁的能力模块。实际落地时通常遵循以下规范：

| 规范 | 具体要求 | 本项目对应实现 |
| --- | --- | --- |
| 单一职责 | 一个 Skill 只解决一类稳定任务，不把面试、简历生成、评分和工具调用混在一起 | `resume-optimizer-skill` 只负责 Markdown 到职业事实的提炼 |
| 明确触发条件 | 写清楚什么输入进入 Skill，什么输入必须拒绝或交给其他模块 | 输入为 Markdown 项目文档、项目复盘或代码说明；岗位匹配和面试出题不属于本 Skill |
| 输入输出契约 | 用结构化 Schema 约束字段、类型、枚举和必填项，不能只依赖自然语言约定 | 输出固定为单条 `project` 事实，并包含 `content`、`evidence_map` 和 `is_verified` |
| 证据可追溯 | 每个重要结论都要能回指原文，避免模型补造职责、技术和指标 | 每条 highlight 绑定 `evidence_map.source_quote` 和 `confidence` |
| 可组合性 | Skill 通过稳定数据接口与 Agent、工具、数据库解耦 | Career Studio 调用提炼服务，Interview Skill 只消费确认后的事实 |
| 幂等和可重试 | 同一输入重复执行不会破坏已有数据，失败可以重试或回退 | Markdown 任务使用独立 `job_id`；结果先作为草稿，不直接覆盖已确认事实 |
| 安全边界 | 用户文档是数据和证据，不应被当成系统指令执行；限制文件类型、大小和用户数据域 | 只支持 `.md`，绑定当前用户和事实，文档内容以证据上下文传入模型 |
| 质量门禁 | 对结构完整性、证据覆盖率、敏感字段和幻觉风险进行校验 | `citation_coverage`、要点数量、角色、技术方法和数字来源都会进入人工复核判断 |
| 可观测性 | 记录输入规模、耗时、模型调用、回退次数和失败原因，方便定位线上问题 | 记录 Markdown 字符数、耗时、是否 fallback、要点数和证据覆盖率 |
| 版本化 | Skill 指令、Schema、Prompt 和评测样本需要可追踪，修改后能够回归比较 | `resume-optimizer-skill/SKILL.md` 独立纳入 Git，并通过测试样例验证输出质量 |

这里的“Skill”更接近企业里的可版本化 Agent 能力模块：Prompt 负责表达任务规则，代码负责权限、流程、Schema 校验、重试和持久化，模型只负责受约束的内容抽取与语言组织。不能把所有控制逻辑都放在 Prompt 中。

### 4. Skill 的结构化提炼设计

Skill 要求模型只返回一个 `project` 事实，核心字段包括：

```json
{
  "fact_type": "project",
  "title": "项目名称",
  "content": {
    "summary": "项目目标、场景和本人角色",
    "role": "原文明确的角色",
    "tech_stack": ["原文明确使用的技术"],
    "highlights": ["动作 + 方法 + 对象 + 结果"],
    "evidence_map": [
      {"claim": "简历要点", "source_quote": "原文证据", "confidence": 0.0}
    ]
  },
  "tags": ["中文标签"],
  "evidence": "可回指原文的证据",
  "is_verified": false
}
```

核心规则：

- 一个项目只生成一条完整事实，不把项目标题、职责和技术栈拆成相互脱离的记录。
- 每条要点尽量包含“动作、技术方法、解决对象、结果或验证”。
- 保留原文中真实存在的数字和指标，禁止模型补造数据。
- 每条要点必须通过 `evidence_map` 回指 Markdown 原文。
- 证据覆盖率不足时标记为需要人工核对，不自动设置为已确认。
- 摘要和要点需要适合后续 A4 简历编辑器继续修改，而不是生成不可编辑的整段文本。

### 5. Skill 的设计步骤和思路

本次不是先写一段 Prompt 再接页面，而是按“职责边界 → 数据契约 → 证据规则 → 执行链路 → 质量验证”的顺序设计：

1. **先拆分职责**：确认简历提炼与面试出题属于不同业务能力，决定新建 `resume-optimizer-skill`，避免继续膨胀 `interview-skills`。
2. **定义输入边界**：只处理 Markdown 技术文档、项目复盘和代码说明；不读取无关用户数据，不负责岗位匹配、ATS 打分和最终 PDF 排版。
3. **设计输出 Schema**：先确定 `title`、`summary`、`role`、`tech_stack`、`highlights`、`evidence_map` 等字段，再编写 Prompt，让模型围绕契约输出。
4. **设计证据链**：要求每条要点对应原文片段，数字和技术只能来自原文；证据不足时输出待核对状态，而不是强行生成完整经历。
5. **设计执行方式**：由于文档上传和 LLM 生成耗时不可控，采用 `FastAPI 202 + Redis + RQ Worker + 前端轮询`，将请求接收和 AI 处理分离。
6. **设计失败策略**：模型超时、JSON 截断、字段缺失或 Redis 不可用时，分别返回可识别状态；Markdown 解析失败时使用确定性规则回退，不返回空数组。
7. **设计人工确认**：提炼结果先回填到编辑表单，默认 `is_verified=false`；用户核对标题、角色、技术栈和要点后才写入可用于投递的事实库。
8. **设计回归验证**：准备包含标题、角色、技术栈、数字指标、列表和代码块的 Markdown 样本，检查输出结构、证据覆盖率、中文标签和禁止编造规则。

这种设计的核心是把“不确定的模型生成”限制在一个可验证的中间步骤中：模型负责抽取和改写，业务代码负责状态机、权限、持久化、证据校验和人工确认。

### 6. 后端实现链路

Markdown 提炼采用“上传接口 + Redis/RQ 异步任务 + 状态轮询”的方式，避免大文档解析和 LLM 生成阻塞 FastAPI 请求：

```text
前端选择 .md
  → POST /api/v1/career/facts/extract-from-markdown
  → 校验扩展名、读取 UTF-8、生成 RQ job
  → Redis career_fact_extraction 队列
  → CareerFact Worker 调用 CareerStudioService
  → Resume Optimizer Skill + LLM 结构化提炼
  → 结果校验/证据覆盖率检查/失败回退
  → 前端轮询 job 状态并回填事实表单
  → 用户编辑、确认后保存为职业事实
```

主要代码位置：

- `app/api/endpoints/career.py`：上传接口和 RQ job 状态查询接口。
- `app/services/task_queue.py`：职业事实提炼队列和任务查询。
- `app/services/career_fact_jobs.py`：RQ Worker 的同步入口和异步任务包装。
- `app/services/career_studio.py`：加载 Skill、构造提炼 Prompt、解析结构化输出和质量校验。
- `app/workers/resume_worker.py`：注册 `career_fact_extraction` 队列。
- `frontend/src/pages/CareerStudio.js`：上传、轮询、错误提示和结果回填。

上传结果默认是“待确认事实”，不会直接写入已确认事实库。用户可以先修改项目标题、摘要、角色、技术栈、要点和核查依据，再点击确认保存；原始 Markdown 作为证据文档绑定到该事实。

### 7. 本次 Skill 调试过程

调试过程按照“先验证链路，再定位数据，再检查模型输出，最后补充降级”的顺序进行：

#### 第一步：验证前端是否真的发起请求

用户反馈上传 `.md` 后页面没有反应。先检查 `CareerStudio.js` 的文件选择回调、`careerService` 的上传方法和浏览器 Network 请求，确认前端需要处理 `202 Accepted`，不能把“任务已创建”当成“提炼已完成”。随后补充 `job_id` 状态轮询、处理中提示和失败提示。

#### 第二步：验证后端任务是否进入队列

检查 `POST /facts/extract-from-markdown` 返回值、Redis 队列名称和 Worker 注册列表，确认任务是否进入 `career_fact_extraction`。同时检查 RQ job 的 `queued`、`started`、`finished` 和 `failed` 状态，区分“前端没有等待”“任务没有入队”和“Worker 执行失败”三类问题。

#### 第三步：定位空结果和 JSON 错误

早期直接对模型文本调用 JSON 解析，遇到 Markdown 代码块、解释性前言、截断 JSON 或字段类型不一致时会抛出异常，前端表现为失败或空数组。调试时保留模型原始响应长度、响应尾部和异常类型，确认问题发生在模型输出格式，而不是数据库写入。

处理顺序是：清理代码块标记 → 解析 JSON → 校验字段类型和必填项 → 规范化字段 → 计算证据覆盖率；任一步失败都进入确定性 Markdown 回退解析器，并返回 `warnings`，让用户知道需要人工核对。

#### 第四步：定位“项目标题和内容分开”的数据问题

检查前端事实卡片、后端事实 Schema 和 Skill 输出后发现，项目标题、角色和技术内容曾经被当成不同展示片段，导致事实不完整。通过固定“单个项目只生成一条 project fact”的输出约束，将标题、角色、技术栈、摘要和 highlights 放入同一条事实，并把原文作为 evidence 保存。

#### 第五步：定位生成内容过短的问题

对比生成结果和原始 Markdown，发现模型倾向于输出项目简介或技术名词列表，没有体现“做了什么、怎么做、解决什么、如何验证”。因此没有简单提高温度或让模型“写得更丰富”，而是把简历表达模板和质量门禁写入独立 Skill：摘要说明场景和角色，highlights 要求 4–6 条，并优先保留技术链路、边界、异常处理和可验证结果。

#### 第六步：增加自动化回归验证

新增 `tests/test_resume_optimizer_skill.py`，目前覆盖确定性回退解析、技术栈与列表提取、证据对齐、以及定制简历回退结果对事实结构的保留。它可以在不调用外部 LLM 的情况下验证核心数据转换逻辑，避免模型服务波动掩盖代码回归。

同时把以下内容作为质量门禁和后续回归样本：

- Markdown 提炼结果必须是一条完整 `project` 事实。
- 标题、角色、技术栈和要点不能被拆成互相脱离的数据。
- 原文中的数字必须保留，原文不存在的数字不能被自动添加。
- 证据覆盖率不足时必须标记为需要人工复核。
- LLM 输出异常时必须有确定性回退，而不是返回空结果。

### 8. 遇到的问题与解决方式

#### 问题一：上传后前端没有反应或等待时间过长

最初如果在 FastAPI 请求内直接调用 LLM，接口会一直等待模型返回，前端无法区分“处理中”和“失败”，大文档还会占用后端请求线程。

解决方式：将提炼改为 Redis + RQ 异步任务。上传接口立即返回 `202 Accepted` 和 `job_id`，前端每隔一段时间查询任务状态，状态为 `completed` 后再回填草稿，失败时显示可重试提示。

#### 问题二：AI 返回内容不是合法 JSON

模型可能返回 Markdown 代码块、解释性前言、截断 JSON 或字段类型不符合预期，直接 `json.loads` 会报错，用户看到提炼失败。

解决方式：

- Prompt 明确要求只返回一个 JSON 对象，不输出代码块和解释。
- 后端先清理代码块标记，再解析 JSON。
- 使用 Pydantic/业务规则校验 `fact_type`、标题、摘要、要点和证据字段。
- 解析失败或模型不可用时使用基于 Markdown 标题、列表和技术栈行的确定性回退解析器，生成待人工核对草稿，而不是返回空结果。
- 保留 `warnings` 和 `quality.requires_review`，让前端明确显示需要人工确认。

#### 问题三：生成的项目经历过短、像摘要，不符合技术简历

早期提炼容易只返回项目名称和几句简介，项目角色、技术路径、数据流、异常处理和验证结果被压缩掉，标题和正文还可能被拆成不同事实。

解决方式：将简历表达规则独立沉淀到 `resume-optimizer-skill/SKILL.md`，要求输出 4–6 条完整 highlights，并按“目标场景 → 本人职责 → 核心实现 → 工程结果”组织内容；同时增加 `evidence_map`，防止为了让句子更像简历而编造技术、指标或职责。

#### 问题四：事实标签或技术栈出现英文，影响中文事实库使用

模型可能直接沿用英文标题、标签或字段描述，导致前端事实库语言不统一。

解决方式：在 Skill 和 Prompt 中明确要求中文标题、中文标签和中文摘要；技术栈名称保留官方英文写法，但角色、摘要、要点和证据说明使用中文；后端对标签做本地化处理，并在保存前统一结构化字段。

### 9. 当前效果与边界

- 用户可以通过事实库上传 `.md` 文件，后台异步生成项目事实草稿。
- 提炼结果包含摘要、角色、技术栈、项目要点、证据和置信度信息。
- 结果先进入人工确认，不会直接成为可投递经历。
- Markdown 原文可绑定到项目事实，后续可在前端编辑、归档，并作为面试评估的证据上下文。
- 模型不可用、JSON 截断或字段不完整时有确定性回退，不再因为一次模型异常返回空数组。
- 当前仍依赖 LLM 的抽取质量；生产环境还可以增加文档版本、对象存储、分块解析、向量检索和离线质量评估。

### 10. 对话记忆管理优化：从固定截断升级为滚动摘要

#### 10.1 背景问题

原有对话上下文主要依赖固定窗口，例如只保留最近几轮消息。这个方案虽然实现简单，但会出现两个问题：

- 用户在早期明确确认的技术选型、约束条件和历史决策，随着会话变长会被直接丢弃。
- 如果把所有历史消息都塞进 Prompt，又会导致输入 Token、模型延迟和调用成本持续增长。

因此本次没有简单扩大截断窗口，而是把“历史持久化”和“模型上下文构建”分离：原始问答继续完整保存，模型只接收经过摘要、检索和预算控制后的上下文。

#### 10.2 设计思路

采用“长期摘要 + 短期窗口 + 原始证据”的分层记忆设计：

1. **原始历史层**：Qdrant 保存当前租户、用户和会话的完整问答轮次，作为可回溯证据。
2. **滚动摘要层**：Redis 保存会话级摘要，记录摘要版本、覆盖时间点、覆盖轮数、模型和更新时间。
3. **短期上下文层**：每次请求保留最近 4 个完整问答轮次，保证当前对话连续性。
4. **证据召回层**：通过 Qdrant 语义检索最多保留 2 条相关原始轮次，用来核验摘要中的关键细节。
5. **预算保护层**：上下文只淘汰完整轮次，不从句子中间截断；摘要生成也只接收完整问答轮次。

这样设计的目的不是删除记忆，而是让不同类型的信息承担不同职责：摘要负责长期连续性，近期消息负责临场语境，原始证据负责事实核验。

#### 10.3 实现链路

```text
用户完成一轮对话
  → Qdrant 异步保存完整问答
  → 达到 8 轮或新增 4 轮
  → 投递 conversation_summary RQ 任务
  → Worker 读取未被摘要覆盖的历史轮次
  → LLM 生成版本化中文滚动摘要
  → Redis 按 tenant:user:chat 保存摘要

下一次用户提问
  → 并行读取 Mem0、Qdrant 当前历史和 Redis 摘要
  → 摘要 + 最近 4 轮 + 最多 2 条相关原始证据
  → 交给 LangGraph / InterviewSkill / 普通聊天流程
```

#### 10.4 主要代码修改

| 文件 | 修改内容 | 设计目的 |
|---|---|---|
| `app/services/conversation_summary.py` | Redis 摘要存取、会话隔离、版本号、分布式锁、摘要 Prompt | 管理摘要生命周期，避免跨用户污染和并发覆盖 |
| `app/services/conversation_summary_jobs.py` | RQ 摘要 Worker，增量读取未覆盖轮次并生成摘要 | 把耗时 LLM 摘要从 FastAPI 主请求中移出 |
| `app/services/task_queue.py` | 增加 `conversation_summary` 队列和入队方法 | 复用现有 Redis + RQ 基础设施 |
| `app/workers/resume_worker.py` | 注册摘要队列 | 让现有 Worker 能消费摘要任务 |
| `app/agent/chat_agent.py` | 读取摘要并组合摘要、近期消息和证据 | 降低 Prompt 长度，同时保留旧事实和可核查依据 |
| `app/services/vector_store.py` | 支持只读 Qdrant 初始化，不强制创建 Embedding 客户端 | 摘要任务只读历史时避免无意义的外部 Embedding 依赖 |
| `tests/test_conversation_summary.py` | 摘要存储、增量覆盖、Prompt 安全和 Worker 逻辑测试 | 验证摘要不会跨会话污染、重复覆盖或丢失完整轮次 |
| `tests/benchmark_memory_context.py` | 固定窗口、语义检索和滚动摘要的离线对比 | 量化上下文长度和早期事实召回效果 |

#### 10.5 为什么使用异步滚动摘要

摘要本身需要调用 LLM，如果在用户提问接口内同步生成，会增加首字延迟，并且模型超时会直接影响问答。因此摘要采用后台 RQ 任务：主请求只读取已经存在的 Redis 摘要；摘要尚未生成、Redis 不可用或任务失败时，自动回退到原有语义检索和近期轮次，不阻断主流程。

摘要不是每轮都生成，而是在达到 8 轮后首次生成，之后每新增 4 轮增量更新一次。这样可以减少重复 LLM 调用，并且只处理“上次摘要之后新增的历史”，避免每次重新总结整个会话。

#### 10.6 测试与优化效果

执行命令：

```bash
./.venv/bin/python -m unittest tests.test_conversation_context tests.test_conversation_summary tests.test_ai_regression -v
./.venv/bin/python -m tests.benchmark_memory_context --turns 8 20 40 80
```

测试结果：

- `11` 项单元测试全部通过，Python 编译检查和 `git diff --check` 通过。
- 固定窗口在测试中无法召回第 1 轮的 Redis + RQ 事实；语义检索和滚动摘要均可召回。
- 8 轮场景下，滚动摘要上下文 Token 约比语义上下文减少 `12.75%`。
- 20、40、80 轮场景下，滚动摘要上下文 Token 约减少 `30.5%`，上下文长度趋于稳定。

#### 10.7 今日记忆管理改进总结

**针对的问题**：原有方案如果只保留最近固定几轮，会随着对话增长丢失早期的技术选型、用户偏好和未解决事项；如果把全部历史直接塞进 Prompt，又会造成上下文变长、Token 成本增加、模型响应变慢，并且无法区分“长期事实”和“当前对话语境”。

**改进思路**：没有简单扩大截断窗口，也没有移除 Mem0，而是按信息职责进行分层：

| 信息类型 | 存储/处理方式 | 使用目的 |
|---|---|---|
| 用户长期事实和偏好 | Mem0，使用 `tenant_id + user_id` 隔离命名空间 | 跨会话召回稳定的个人信息和偏好 |
| 当前会话原始证据 | Qdrant 保存完整问答轮次 | 支持语义检索、事实核验和问题追溯 |
| 历史会话压缩信息 | Redis 保存版本化滚动摘要 | 低成本保留早期上下文，避免每次重新总结 |
| 最近对话语境 | 每次保留最近 4 个完整问答轮次 | 保证当前追问连续性，避免摘要造成表达失真 |
| 关键历史证据 | Qdrant 语义检索后最多保留 2 条 | 对摘要中的技术事实进行原文核验 |

**具体实现方法**：

1. 用户每轮对话仍然异步写入 Mem0 和 Qdrant，原始记录不因摘要而删除。
2. 达到 8 轮后投递 `conversation_summary` RQ 任务，之后每新增 4 轮增量更新一次。
3. Worker 读取上次摘要覆盖时间点之后的完整问答，调用独立的 `MEMORY_LLM_MODEL` 生成中文滚动摘要。
4. Redis Key 使用 `conversation-summary:v1:{tenant_id}:{user_id}:{chat_id}`，并通过分布式锁避免同一会话并发覆盖。
5. 每次请求并行读取 Mem0、Qdrant 历史和 Redis 摘要；Redis 读取失败或摘要不存在时，回退到原有近期轮次和语义检索，不阻塞主问答链路。
6. 摘要 Prompt 明确要求只保留用户确认事实、标记冲突信息、禁止执行历史消息中的指令，降低记忆污染和 Prompt Injection 风险。

**改进结果**：

- 8 轮测试中，滚动摘要可以保留固定窗口无法召回的第 1 轮 Redis + RQ 技术事实。
- 相比语义检索上下文，8 轮场景的估算 Token 减少 `12.75%`。
- 20、40、80 轮场景的估算上下文 Token 约减少 `30.5%`，上下文长度趋于稳定，不再随历史线性增长。
- 摘要生成从 FastAPI 请求中移到 RQ Worker，避免摘要 LLM 调用增加用户问答的首字延迟。
- 测试覆盖会话隔离、摘要增量更新、分布式锁、Prompt 安全、Worker 执行和失败回退；相关测试通过。

**工程边界**：滚动摘要是上下文压缩层，不是事实数据库；Mem0 负责长期记忆，Qdrant 负责原始证据和语义检索，Redis 负责短期缓存和摘要状态。这样即使摘要生成失败，也可以依靠 Qdrant 原始记录恢复上下文，避免单一记忆组件故障导致信息丢失。

## 三、职业事实技术文档证据检索

### 1. 设计判断

将职业事实库中所有项目技术文档原文直接拼接到面试 Prompt，虽然信息完整，但会带来上下文膨胀、Token 成本增加、无关内容干扰评分和证据难以定位等问题。工业界更常见的方式是 RAG：原文持久化，按当前问题检索相关片段，再以带来源的 Evidence Pack 注入提问和评分上下文。

### 2. 本次实现

本项目先落地轻量、可解释的证据检索层，避免在当前小服务器上为每次面试重复调用 Embedding：

| 环节 | 实现方式 | 目的 |
|---|---|---|
| 文档切分 | 按 Markdown 标题、段落和长度切分为约 1400 字符片段 | 避免整篇文档进入 Prompt，尽量保持章节语义完整 |
| 相关性排序 | 使用依赖无关的 BM25 风格词法排序，对标题/章节命中增加权重 | 优先召回当前问题相关的技术内容，避免把整份文档塞进 Prompt |
| 元数据绑定 | 每个片段保留 `fact_id`、文档 ID、章节和 `chunk_id` | 评分结果可以回溯到具体项目事实和原文片段 |
| 数量控制 | 面试请求最多召回 4 个片段、最多 3 份文档，每份文档最多 2 个片段 | 防止单个大文档或单个项目占满上下文 |
| 上下文预算 | 单个片段最多 900 字符，Evidence Pack 最多 3200 字符 | 控制 Prompt 长度、延迟和 Token 成本 |
| 查询构造 | 使用上一道问题、当前回答和 JD 联合检索 | 让提问和评分使用同一组相关证据 |
| 缓存失效 | Redis Key 包含用户、事实 ID、查询、文档版本、检索器版本和预算参数 | 文档编辑或检索策略升级后不复用旧证据 |

上传和编辑后的 Markdown 仍然完整保存到 `career_knowledge_documents`；面试请求只读取当前用户未归档文档的相关片段，不修改原始资料。

### 3. 数据流

```text
职业事实 + Markdown 技术文档
  → 数据库完整保存
  → 面试请求构造“上一道问题 + 当前回答 + JD”查询
  → Markdown 分块与相关性排序
  → 生成带 fact_id/chunk_id 的 Evidence Pack
  → 面试 Agent 生成下一道问题
  → EvaluationAgent 复用同一 Evidence Pack 评分
  → knowledge_evidence 引用具体证据或返回空数组
```

### 4. 为什么这样设计

- **完整性与上下文长度解耦**：原文保存在数据库，模型只看到当前任务需要的证据。
- **提问与评分依据一致**：避免面试官依据一套资料提问、评估器依据另一套资料打分。
- **可解释**：每个片段带有职业事实和文档章节标识，评分可以追溯来源。
- **安全**：技术文档作为证据传入，不作为系统指令执行；评估 Prompt 明确要求无直接证据时返回“证据不足”。
- **可演进**：当前先用可解释的关键词/章节检索控制服务器成本，后续可在同一 `chunk_id` 和元数据契约上替换为 Qdrant 向量检索或混合检索，不需要改评分接口。

### 5. 测试与结果

新增检索测试，覆盖：

1. 大文档能够按 Markdown 章节拆分，后半部分相关内容不会因为只取文档开头而丢失；
2. 查询会优先选择相关项目文档和相关章节；
3. Evidence Pack 包含 `fact_id`、`chunk_id`，并遵守最大字符预算；
4. 不相关文档不会占满评分上下文。

同时保留原有对话记忆测试和压测结果。当前实现的效果是：技术文档不再整篇拼入 Prompt，提问和评估通过同一个版本化查询缓存复用证据上下文；面试请求最多使用 4 个相关片段，每个片段最多 900 字符，上下文预算收紧到 3200 字符，降低无关内容干扰并限制 Token 成本。后续生产评估还应继续采集证据命中率、评分证据覆盖率、P95 延迟和人工复核一致率。

## 七、证据缓存、评估去重与超时治理

### 1. 为什么改

此前每次面试请求都会在 FastAPI 请求路径内重新切分和排序技术文档；同一答案如果因为前端重试、网络重连或 Worker 重复投递而再次评估，也会再次调用远程模型。OpenRouter 的响应缓存只能复用完全相同的请求，而且并发请求不会自动合并，因此不能替代应用层的幂等和 single-flight 控制。

### 2. 设计与数据流

```text
职业事实文档版本 + 当前问题/JD/回答
  → 版本化 Evidence Pack Key
  → Redis 命中：直接复用
  → Redis 未命中：线程池内检索、限制为 5000 字符、写入 15 分钟缓存
  → 同一 Evidence Pack 同时进入提问和 EvaluationRequest

EvaluationRequest
  → 版本化评估 Key（Rubric、模型、请求内容）
  → Redis 命中：直接写回 completed
  → 未命中：SET NX 获取 60 秒锁
  → 其他 Worker 已处理时等待缓存，避免重复 LLM 调用
  → 只有 evaluation_mode=llm 的正常结果进入 24 小时结果缓存
  → fallback 结果不缓存，防止临时故障污染后续评估
```

### 3. 工程实现

| 模块 | 实现细节 | 解决的问题 |
|---|---|---|
| `app/services/redis_cache.py` | 统一 JSON/文本读写、TTL、SET NX 锁和安全释放；Redis 异常只降级为 cache miss | 缓存故障不影响主流程 |
| `career_knowledge.py` | Key 包含租户、用户、查询、检索器版本、文档 ID、`source_hash`/编辑后内容 hash 和预算参数 | 文档上传或编辑后自动失效，不读旧证据 |
| `evaluation_cache.py` | Key 包含 Rubric 版本、模型版本和完整 `EvaluationRequest` 的哈希 | 相同答案幂等，不把原始简历内容放进 Redis Key |
| `evaluation_jobs.py` | 先查结果缓存，再用 Redis 锁合并并发请求；任务完成后写回结果 | 前端重试、重复入队不会重复消耗模型调用 |
| `interview_evaluator.py` | OpenRouter 响应缓存通过 `OPENROUTER_RESPONSE_CACHE_ENABLED` opt-in | 在确认数据保留策略后再启用 Provider 侧缓存 |
| `config.py` | 评估硬超时 20 秒 × 最多两次调用，RQ 作业超时收紧为 60 秒 | 避免远程模型长时间占用 Worker |

### 4. 测试与验证

- 证据缓存测试验证：同一查询和文档版本第二次命中；编辑文档内容后 Key 变化并重新构建。
- 评估队列测试验证：相同 `EvaluationRequest` 连续投递两次，`EvaluationAgent.evaluate()` 只执行 1 次，第二次返回 `evaluation_cache_hit=true`。
- 缓存层测试验证：Key 对请求内容敏感、Provider 缓存默认关闭、开启后发送正确的 `X-OpenRouter-Cache` 和 TTL 配置。
- `./.venv/bin/python -m compileall -q app tests` 通过；缓存相关 unittest 共 4 项通过，评估队列 unittest 2 项通过。

这些是功能正确性验证，不是线上性能收益的假设数据。上线后应继续记录 `evidence_cache_hit_rate`、`evaluation_cache_hit_rate`、重复评估抑制次数、模型调用次数、P50/P95 延迟和 Token 消耗，再用相同多用户压测对比优化前后结果。

### 5. 行业实现边界

LLM-as-a-Judge 仍然使用结构化 Rubric、证据链核验和版本化评估结果；技术文档是检索到的候选人证据，不是系统指令。应用层 Redis 缓存负责业务幂等和并发合并，Provider 侧缓存只作为可选的额外优化：OpenRouter 官方说明完全相同请求才会命中，且并发请求不会自动合并，因此本项目保留 Redis single-flight 作为第一道保障。

## 四、Tool Calling 参数可靠性与运行指标

### 1. 发现的问题

之前只能确认 MCP 工具能够被加载和调用，系统没有单独记录工具参数错误、业务校验失败、超时、重复调用和自动修正结果。因此无法回答“Tool Calling 是否稳定”，也不能把通用 AI 请求成功率等同于工具调用成功率。

### 2. 实现方式

本次将工具调用拆成“模型生成 → Schema 校验 → 业务校验 → 工具执行 → 错误修正”几个阶段进行观测：

| 改动 | 实现方式 | 作用 |
|---|---|---|
| MCP 参数观测 | 在 `Researcher` 和 `Scrapper` Agent 的 `ainvoke` 中注入 LangChain `BaseCallbackHandler` | 记录每次工具开始、结束和异常，不保存原始参数 |
| 参数脱敏 | 对工具输入做 JSON 规范化后计算 SHA-256 | 可识别重复调用，同时避免把 URL、查询内容等原始数据写入指标表 |
| 错误分类 | 按异常文本区分 `schema`、`business`、`execution` 和 `timeout` | 区分是字段类型错误、业务参数错误还是下游服务故障 |
| 业务校验 | `search` 拒绝空查询和超长查询；`web_scrapping` 校验 HTTP/HTTPS URL 和域名 | 让非法 URL、空参数等问题在工具边界提前失败 |
| 自动修正统计 | 同一 Agent 调用中，失败工具后续再次成功调用同名工具，记为一次修正成功 | 衡量模型收到错误反馈后能否恢复 |
| 指标持久化 | 新增 `tool_call_metrics` 表和 `/api/v1/metrics/tool-calls/summary` 接口 | 支持按用户查看工具调用成功率、错误率和 P95 延迟 |

模型侧增加了“工具参数错误后最多修正一次、禁止重复无效调用”的约束；真正的参数安全仍由 MCP/Tool Schema 和工具函数业务校验保证，Prompt 不是唯一防线。

### 3. 指标定义

- `Schema 错误率 = schema 校验失败次数 / 工具调用总次数`。
- `业务错误率 = 业务校验失败次数 / 工具调用总次数`。
- `工具成功率 = 成功执行次数 / 工具调用总次数`。
- `自动修正成功率 = 失败后再次成功执行次数 / 触发修正次数`。
- 同时记录超时率、执行异常率、平均延迟、P95 延迟和重复调用情况。

### 4. 验证结果

新增 `tests/test_tool_call_metrics.py`，覆盖：

1. Schema、业务校验和超时异常的分类；
2. 工具失败后再次成功时的自动修正识别；
3. 成功率、错误率、修正率和 P95 延迟汇总计算。

执行结果：`tests.test_tool_call_metrics` 与 `tests.test_ai_regression` 共 `9` 项测试通过，Python 编译检查和 `git diff --check` 通过。服务运行后可以调用 `/api/v1/metrics/tool-calls/summary` 查看真实数据；当前历史数据为空时返回 0 是正常现象，必须先触发 Researcher 或 Scrapper 工具调用。

这项改造的直接价值是把“模型调用看起来成功”变成可量化的工具链路质量：可以定位参数错误来自 Schema、业务规则还是下游服务，并用修正成功率和 P95 延迟评估 Agent 的实际可靠性。

## 六、面试评估实时化优化

### 1. 问题定位

本次排查发现，单题评估实际上已经在候选人提交答案后通过 `EvaluationRequest` 投递到 Redis + RQ 队列，并由 `evaluation_jobs.process_evaluation_job` 异步执行；问题主要出在展示链路：前端只在检测到“本场面试已结束”时请求整场报告，作答过程中只刷新消息，不读取评估状态，因此用户看不到 queued、processing 和 completed 状态。同时，整场报告接口会为缺少参考答案的题目再次调用 LLM，实时查看报告时会产生额外等待。

### 2. 设计与实现

| 目标 | 实现 | 技术原因 |
|---|---|---|
| 逐题可见 | 报告接口把 `evaluation_status`、`evaluation`、`evaluation_error` 绑定到 `interview_questions`，在右侧“问答记录”逐题展示 | 将异步任务状态映射到具体问答记录，而不是把评分混在聊天气泡中 |
| 自动刷新 | 面试进行中每 1.5 秒轮询会话消息和部分报告；评估全部完成后自动停止 | 采用短轮询兼容现有 RQ/Qdrant 数据链路，不要求新增 WebSocket 连接 |
| 降低实时报告等待 | 报告接口增加 `partial=true`；部分报告跳过缺失参考答案的二次 LLM 生成 | 实时场景优先返回已有评分，完整参考答案只在最终报告中生成 |
| 避免重复请求 | 增加前端 `reportInFlightRef`，同一会话的静默轮询不会并发发起多个报告请求 | 避免网络慢时定时器堆积，降低浏览器和后端压力 |
| 隔离评估任务 | 新增 `app.workers.evaluation_worker`，只监听 `interview_evaluation` 队列；原通用 Worker 不再抢占该队列 | 简历解析、代码执行等慢任务不会阻塞面试评分 |
| 控制模型输出 | 评估最大输出 Token 从 1536 调整为 1024，并限制摘要、证据、优缺点条数和长度 | 评分所需的是结构化结论，不应让冗长解释占用生成时间 |

### 3. 当前数据流

```text
候选人提交答案
  → FastAPI 保存对话点和 evaluation_status=queued
  → Redis interview_evaluation 队列
  → 独立 Evaluation Worker
  → EvaluationAgent 调用模型并写回 processing/completed/failed
  → 前端每 1.5 秒读取会话消息
  → 对应回答下显示状态、分数、判定和摘要
```

### 4. 测试与验证

- `tests.test_interview_assessment` 与 `tests.test_interview_evaluation_queue` 共 14 项测试通过；新增测试验证部分报告不会调用 `_generate_reference_answers`。
- `./.venv/bin/python -m compileall -q app tests` 通过，`git diff --check` 通过。
- `npm run build` 成功，仅保留项目原有 ESLint 警告。
- `chatbot-evaluation-worker.service` 已启动并监听 `interview_evaluation`；运行内存约 25.2 MB。通用 Worker 当前监听 `resume_parse`、`career_fact_extraction`、`code_execution` 和 `conversation_summary`，不再监听评估队列。

### 5. 结果与边界

现在不是等整场结束才评估：每个有效回答都会独立入队，处理完成后会在该回答下显示分数和摘要；评估任务仍受远程模型响应速度影响，但不会阻塞提交答案，也不会被其他 RQ 队列排队拖延。若模型或网络失败，前端会显示失败状态，后续可继续补充重试按钮、任务超时补偿和 SSE 推送以进一步减少轮询。

本次实际失败样本的根因已从 RQ FailedJobRegistry 栈追溯确认：历史任务使用 `EVALUATION_LLM_MAX_TOKENS=1536`，DeepSeek 返回的结构化结果因达到输出上限而触发 `LengthFinishReasonError`；另有远程模型请求超过 RQ 的 `120s` 作业超时。已将默认配置和 `.env.example` 统一为 `1024`，增加评估字段长度约束，并让失败原因持久化到问答记录，避免只显示笼统的“评估失败”。

## 七、评估降级与参考答案链路修复

### 1. 修复动机

用户在已结束的面试中看到部分题目长期显示：

```text
综合 50 分
证据不足
规则降级
低置信度
远程模型暂时不可用，已使用规则降级评估
参考答案：暂时无法生成参考答案。
```

这不是评分规则主动判定为“证据不足”，而是历史评估任务在远程模型调用失败后进入了规则降级分支。降级结果已经写入 Qdrant，后续打开会话时会直接读取历史结果，不会因为模型恢复而自动重算；同时，参考答案生成和评估使用了不同的结构化输出链路，模型返回字段不完整时会直接进入占位文本。

### 2. 排查过程

| 排查步骤 | 观察结果 | 结论 |
|---|---|---|
| 查看 `chatbot-evaluation-worker` 日志 | 多次出现 `LengthFinishReasonError`、`TimeoutError`，单题耗时约 30.3～40.0 秒 | 评估 Worker 没有卡死，失败发生在远程模型调用和输出解析阶段 |
| 检查 OpenRouter 最小请求 | `deepseek/deepseek-v4-flash` HTTP 200，短 JSON 请求约 1.25 秒返回 | API Key、模型名和网络链路正常，不是模型完全不可用 |
| 对比 LangChain 结构化输出方式 | 默认 Tool/Function Calling 结构化请求较慢；短请求使用 JSON Mode 可正常返回 | 当前模型对 Function Calling 结构化输出兼容性和延迟不稳定 |
| 检查历史 Qdrant 记录 | 旧记录的 `evaluation_status=completed`，但 `evaluation_mode=fallback`，因此前端不会自动重试 | 页面显示的是历史降级结果，不是当前实时调用结果 |
| 检查参考答案生成 | 参考答案只读取 `expected_key_points` 和 `correction_suggestion`，降级结果通常没有这两个字段 | 降级评估完成后会显示“暂时无法生成参考答案” |

### 3. 技术改造

#### 3.1 评估模型调用改为 JSON Mode

在 `app/services/interview_evaluator.py` 中，将原来的：

```text
with_structured_output(LLMAnswerEvaluation)
```

改为：

```text
ChatOpenAI.bind(response_format={"type": "json_object"})
→ 读取模型文本
→ 去除 Markdown 代码围栏
→ JSON 解析
→ rubric_scores 兼容 dict/list 两种格式
→ LLMAnswerEvaluation.model_validate()
```

这样保留了 Pydantic Schema 校验，同时避免把模型强制绑定到 Tool Calling。对于 `rubric_scores`，兼容模型返回的对象格式，例如：

```json
{"rubric_scores": {"technical_correctness": 3}}
```

会被转换为系统内部统一格式：

```json
{"rubric_scores": [{"dimension": "technical_correctness", "score": 3}]}
```

#### 3.2 紧凑 Prompt 真正独立

之前的“紧凑重试”只是把一句兜底说明追加到完整 Prompt 后面，技术资料、JD 和评估要求仍然全部重复发送，无法真正降低上下文长度。

现在改为独立的最小 Prompt：

- 问题最多 700 字符；
- 回答最多 1800 字符；
- 技术证据最多 1200 字符；
- Rubric 维度完整保留；
- 数组最多 2 项，减少无效生成内容。

这形成两级调用策略：正常请求保留完整评估上下文；正常请求超时或解析失败时，使用独立紧凑 Prompt 重试，而不是重复发送完整请求。

#### 3.3 降级结果支持重新评估

新增接口：

```text
POST /api/v1/chats/{chat_id}/messages/{point_id}/evaluation/retry
```

该接口现在同时支持：

- `evaluation_status=failed` 的任务；
- `evaluation.evaluation_mode=fallback` 的历史降级结果。

重新评估时会复用原始问题、候选人回答、岗位、JD、简历和技术证据，重新投递 `interview_evaluation` RQ 队列，不改变原始问答内容。前端在右侧“问答记录”中为规则降级结果增加“重新评估”按钮，避免用户重复提交答案。

#### 3.4 参考答案增加可解释兜底

参考答案生成现在按以下顺序处理：

1. 优先读取 LLM 评估返回的 `expected_key_points` 和 `correction_suggestion`；
2. 如果是规则降级结果，则根据 `rubric_scores.missing_points` 生成“参考要点（规则降级生成）”；
3. 只有远程参考答案生成和降级 Rubric 都不可用时，才显示占位文本。

参考答案生成链路也改为 JSON Mode，并通过结构化 Schema 校验 `items[index, reference_answer]`。

### 4. 优化指标

| 指标 | 优化前 | 优化后 | 说明 |
|---|---:|---:|---|
| 最小 OpenRouter JSON 请求耗时 | — | 约 1.25 秒 | HTTP 200，证明远程模型和网络链路可用 |

### 6. 使用说明与边界

历史已经落库的“规则降级”结果不会自动重算，这是为了避免用户每次刷新页面都重复消耗模型额度。用户需要在右侧问答记录点击“重新评估”；任务完成后，前端轮询会读取新的 `evaluation_status` 和评估结果。

本次解决的是模型调用兼容性、输出解析和历史结果补偿问题；远程模型仍可能受网络、供应商限流或区域策略影响，因此保留可解释 Rubric 降级机制。生产环境还应继续监控 `llm_success_rate`、`fallback_rate`、`evaluation_latency_p50/p95`、`json_parse_error_rate` 和重新评估成功率。

### 7. 代码题职业事实检索与评估队列修复

#### 7.1 问题与动机

排查发现，面试接口在所有面试问题上都会读取职业事实文档并构建 RAG 上下文。代码题主要依据题目、候选人代码、运行结果和通用评分 Rubric，不需要将项目经历文档拼接进 Prompt。这种无差别检索会增加数据库查询、向量检索和 Prompt 长度，造成不必要的等待和 Token 消耗。

同时，评估任务虽然使用 RQ 异步执行，但原先没有配置自动重试；初始化或状态写入发生在异常保护范围外时，任务可能只留下失败状态。多个评估任务排队时，失败任务缺少重试和清晰状态回写，容易表现为后续任务一直等待或无法确认是否执行。

#### 7.2 技术实现

1. 在 `app/services/interview_assessment.py` 新增 `should_use_career_evidence()`，先排除代码题标记，再只匹配“项目、实习、工作经历、项目经历”等明确语义。
2. 在 `app/api/endpoints/chat.py` 使用上一条 AI 面试官问题进行判断，而不是使用用户回答判断，避免用户回答中提到“项目”导致代码题误触发 RAG。
3. 对项目经历和实习经历问题保留职业事实文档查询、缓存上下文构建和证据注入；代码题、系统设计题、技术原理题则显式将 `knowledge_context` 置空。
4. 在 `app/services/task_queue.py` 为评估任务配置 `Retry(max=2, interval=[5, 15])`，单个任务最多执行 3 次，失败后延迟重新入队，不阻塞后续任务。
5. 在 `app/workers/evaluation_worker.py` 启用 `with_scheduler=True`，保证 RQ 能执行带间隔的延迟重试。
6. 将评估队列超时从 120 秒提高到 180 秒，覆盖模型调用、紧凑重试、缓存锁等待和状态回写等耗时，配置同步到 `.env`、`.env.example` 和 `app/core/config.py`。
7. 将评估任务初始化、`processing` 状态写入、模型调用和 `failed` 状态回写统一放入异常保护范围；即使初始化或模型调用失败，也尽量回写可查询的失败状态。

### 8. LLM 评分 0 分误判修复

#### 8.1 根因

原评分链路在模型没有返回完整 `rubric_scores` 时，会用基础维度字段补齐缺失 Rubric；而基础维度在 Pydantic Schema 中默认值为 `0`，因此“模型输出不完整”被错误转换成了“候选人所有维度均为 0 分”。这会造成评分结果看似确定，实际缺少有效评估依据。

#### 8.2 按 LLM-as-a-Judge 方法改造

1. 将 Rubric 作为评分契约，要求模型覆盖当前题型的全部维度，每个维度只能返回 `0-4` 分。
2. 增加维度完整性校验，检查缺失维度、重复维度、多余维度和分数越界，不再静默使用默认 0 分补齐。
3. 主模型输出不完整时，自动使用紧凑 Prompt 重试；两次结构化输出都不合格时才进入规则降级。
4. 规则降级保留评分依据、可观察信号、缺失点和失败原因，避免返回不可解释的裸分。
5. 正常 LLM 评分也写入 `evaluation_basis`，记录 Rubric 版本、权重计算公式和零分定义，支持结果审计。
6. 使用 Pydantic 字段约束限制 Rubric 分数范围，避免模型返回负数或大于 4 的非法分数。

#### 8.3 现在 0 分的定义

只有模型完整返回所有 Rubric 维度，并且每个维度都明确评为 `0`，综合分才会是有效的 0 分。若只是缺少字段、重复字段、分数越界或 JSON 结构异常，会先重试，失败后转为规则降级；规则降级不会因为字段缺失直接返回 0 分。

#### 8.4 验证结果

新增测试覆盖不完整 Rubric、模型重试、规则降级和评分依据写入；全量测试结果为 `51 tests OK`，后端和评估 Worker 均为 `active`。

### 9. 面试评分强制重评与可靠性复核

#### 9.1 重评动机

上一版历史结果中存在两条 `0` 分记录。为了确认不是旧缓存或历史错误数据影响结果，本次没有直接调用普通重试接口，而是增加一次性 `force_refresh` 标记，跳过 Redis 中已有的评估缓存，使用当前 Rubric 校验、零分保护和降级链路重新计算，并将结果覆盖回原有问答记录。

#### 9.3 是否符合工业界标准

当前方案符合业界 LLM-as-a-Judge 的核心工程实践，但定位是“可控的工程化 MVP”，不能等同于已经完成大规模生产校准的商业评分模型。

| 能力 | 当前实现 | 可靠性评价 |
|---|---|---|
| 评分标准 | 按题型拆分 Rubric，并使用版本号管理 | 可控 |
| 输出格式 | JSON Mode + Pydantic Schema + Rubric 完整性校验 | 可控 |
| 分数计算 | 后端按权重确定性计算，不信任模型直接给出的综合分 | 可复现 |
| 证据约束 | 核验回答、简历和技术文档中的证据，过滤无法核验内容 | 可审计 |
| 异常处理 | 紧凑重试、规则降级、失败状态和队列自动重试 | 稳定性较好 |
| 结果解释 | 保存 Rubric 分项、缺失点、证据、评分依据和评估模式 | 可解释 |
| 评分一致性 | 暂无人工标注集、多人评审一致性和离线校准结果 | 仍需补强 |

因此，当前评分在“流程可控、格式可控、计算可复现、失败可降级”方面是可靠的；但 LLM 对技术回答的语义判断仍存在模型偏差和随机性，不能把单次评分直接作为真实招聘决策。下一步应建立带人工标准答案和分数的 Golden Set，统计与人工评分的相关性、不同题型的误差、重复评估一致性和模型版本漂移，再决定是否用于正式筛选。

### 10. 历史缓存覆盖新评分问题修复

#### 10.1 问题根因

强制重评虽然跳过了缓存读取，但当新结果进入规则降级时，旧的 LLM 评估缓存没有被删除。随后历史任务再次执行并命中旧缓存，将原来的 0 分重新写回 Qdrant，因此前端报告仍显示 0 分。

#### 10.2 修复方案

1. 增加 Redis 缓存删除能力。
2. `force_refresh` 执行前先删除当前评估请求对应的旧缓存 Key，再调用模型或规则降级。
3. 后续普通任务只能读取本次重评后的新缓存，不能恢复旧的 0 分结果。
4. 增加强制刷新缓存测试，验证旧缓存不会参与重评。

#### 10.3 验证结果

原来前端显示 0 分的 Tool Calling 评估记录重新计算后为 `61 分`，Qdrant 原始记录和 `InterviewReportBuilder` 生成的报告结果均为 `61 分`，评估状态为 `completed`、模式为 `llm`。当前评估队列为 `queue=0`、`started=0`。
